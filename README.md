# OhBeat

Маркетплейс битов: продюсеры продают лицензии на инструментальные треки, артисты покупают их с автоматическим лицензионным договором и получают файлы по защищённым временным ссылкам.

Это MVP, построенный строго по системно-аналитической документации из соседнего репозитория [`OhBeat-System-Analysis`](../OhBeat-System-Analysis). Продукт не выходит в продакшен, но написан как настоящий: транзакции, статусные модели, резервы, идемпотентность, повторы, проверка прав, единый формат ошибок. Внешний мир (ЮKassa, SMS и email, S3) заменён моками, которые ведут себя по контрактам настоящих сервисов, включая сбои.

## Что умеет продукт

| Кто | Что делает |
| --- | --- |
| **Гость** | Слушает превью в каталоге (стриминг с HTTP Range), фильтрует по жанру, темпу, тональности и цене, смотрит страницы битов и продюсеров |
| **Артист** | Регистрируется с согласиями (ПД, соглашение о ПЭП); кладёт лицензии в корзину (цены продюсеров + комиссия сервиса сверху); оформляет заказ; платит через ЮKassa (двухстадийно, со сплитованием между продюсерами); подписывает Exclusive кодом из SMS; получает PDF-договоры и ссылки на файлы на 1 час в «Моих покупках» |
| **Продюсер** | Подключается к продажам (налоговый статус, ID продавца в ЮKassa); загружает бит прямо в S3 (WAV, обложка, ZIP со стемами); фоновый Media Worker проверяет файлы, ищет вирусы, накладывает голосовой тег и делает превью; ведёт «Мои биты» и «Мои продажи» |
| **Администратор** | Читает Audit Log с фильтрами (журнал только на добавление), ведёт жанры и стоп-лист, разбирает биты, застрявшие в обработке после всех повторов (DLQ) |

Лицензии: **Basic** (MP3), **Premium** (MP3 + WAV), **Trackout** (+ стемы), **Exclusive** (всё + исключительные права, бит уходит из продажи; резерв на 15 минут на время оформления, подпись кодом из SMS).

## Запуск с нуля — одна команда

Нужен только Docker Desktop (Windows, macOS) или Docker Engine с Compose v2.24+ (Linux).

```bash
docker compose up --build
```

Что происходит при первом старте (5–10 минут, дольше всего собирается MinIO из исходников, ADR 0008):

1. PostgreSQL, RabbitMQ, MinIO и мок ЮKassa поднимаются и проходят проверки готовности.
2. `storage-init` создаёт бакеты `temp-uploads` (автоочистка через 24 ч), `private-media`, `public-media` (публичное чтение — вместо CDN).
3. `migrate` применяет миграции (`0001` — ровно `schema.sql` из документации, `0002`, `0003` — дополнения, ADR 0007) и сиды: жанры, лицензии, стоп-слова, демо-пользователи.
4. Стартуют Core API, outbox-relay, планировщик, обработчик результатов, Media Worker и фронтенд.
5. `demo-seed` публикует 16 демо-битов двух продюсеров настоящим путём (API → MinIO → Worker) и завершается.

Настройки берутся из [`.env.example`](.env.example). Чтобы что-то поменять, создайте рядом `.env` (он в `.gitignore`) только с нужными строками — они перекроют значения по умолчанию.

### Демо-аккаунты

Логины и пароли — в [`.env.example`](.env.example), переменные `SEED_*`: Артист, Продюсер «Test Producer», второй Продюсер «Nova Sound» (чтобы в одном платеже было два продавца) и Администратор.

### Где смотреть то, что «ушло наружу»

- **SMS с кодом подписи и письма** мок пишет в лог: `docker compose logs api | grep SMS`, `docker compose logs api media-results | grep EMAIL`. Те же сообщения лежат во «входящих» на томе `mock-inbox` (их читает сквозной тест).
- **Платежи и перечисления продавцам** — пульт мока ЮKassa.
- **Задачи Media Worker, повторы, DLQ** — веб-интерфейс RabbitMQ.

## Сценарии для ручной проверки

1. **Публикация:** Продюсер → «Загрузить бит» → прогресс загрузки каждого файла прямо в MinIO → «Мои биты»: «Обработка» → «Опубликован» (или «Отклонён» с причиной). Сломанный антивирус: `ANTIVIRUS_MODE=unavailable docker compose up -d media-worker`.
2. **Каталог:** фильтры в адресе страницы, Play — в DevTools видно `206 Partial Content`.
3. **Покупка Basic у двух продюсеров:** корзина → оформление с офертой → страница оплаты мока → «Успешная оплата» → ссылки на файлы и PDF-договор → «Мои покупки» (сверьте `SHA-256` с файлом) → пульт мока: деньги разошлись продюсерам, комиссия — платформе.
4. **Сбои оплаты:** «Отказ банка» → «Оплатить снова»; в пульте поломка `500 × 4` для `create` → «Платёжный сервис временно недоступен»; «Холд без уведомления» → через 60 с текст «Оплата обрабатывается…» → вебхук из пульта → оплачено; «Отправить вебхук ещё раз» одновременно → в логе `duplicate`.
5. **Exclusive:** резерв 15 минут → текст договора → «Подписать» → код из лога → неверный код (попытки) → верный → оплата → бит исчез из каталога, в PDF штамп ПЭП.
6. **Гонка за Exclusive** проверяется автотестом (`test_fr18_race_of_buyers_for_one_exclusive`): 10 параллельных заказов → ровно один резерв.
7. **Администрирование:** Audit Log с группой `payment.*`; удалить используемый жанр нельзя; зависший бит → «Повторить обработку».

Подробные шаги и что именно смотреть в БД — в отчётах по срезам [`docs/slices/`](docs/slices).

## Тесты

| Набор | Команда | Сколько |
| --- | --- | --- |
| Core API (pytest на настоящих PostgreSQL, RabbitMQ, MinIO) | `docker compose exec api pytest` | 287 |
| Media Worker | `docker compose exec media-worker pytest` | 32 |
| Мок ЮKassa | `docker compose exec yookassa-mock pytest` | 15 |
| Фронтенд (Vitest) | `docker compose exec frontend npm test` | 43 |
| **Сквозной путь** (Playwright, Chromium и WebKit) | `docker compose --profile e2e run --rm e2e` | 1 сценарий × 2 браузера |

Сквозной тест проходит весь путь через интерфейс: регистрация продюсера → данные для договора → подключение к продажам → загрузка бита с обложкой, WAV и стемами → обработка Worker'ом → публикация → регистрация артиста → покупка Basic с оплатой → PDF-договор и его хэш в «Моих покупках» → письмо продюсеру → покупка Exclusive: резерв, текст договора, код из SMS (сначала неверный) → оплата → стемы → бит пропал из каталога. Отчёт с трассировкой: `frontend/playwright-report/`.

Обязательные тесты из CLAUDE.md: гонка двух (и десяти) покупателей за Exclusive, повторный вебхук (подряд и одновременно), повторная доставка сообщения из очереди, истёкший резерв при `waiting_for_capture`, оплата после `expired`, сумма `transfers` и комиссии.

## Как устроено

```
Браузер ──► Frontend (React, Vite) ──/v1──► Core API (FastAPI) ──► PostgreSQL
   │                                           │   │  outbox ─► outbox-relay ─► RabbitMQ ─► Media Worker (FFmpeg)
   │ presigned POST / GET                      │   │                                ▲            │
   └──────────────────────────────► MinIO (S3) ◄───┼────────────────────────────────┼────────────┘
                                                   │       media-results ◄── beat.media.processed
                     мок ЮKassa ◄─ платежи, capture/cancel ─┤
                     мок ЮKassa ── вебхуки ────────────────►│      планировщик: резервы, заказы, зависшие холды
```

- **Модульный монолит Core API** (`backend/app/`): `auth`, `users`, `catalog`, `orders`, `payments`, `contracts`, `signature`, `purchases`, `admin`, `background`.
- **Media Worker** (`worker/`) — без HTTP и без доступа к БД: только очередь и S3.
- **Transactional outbox:** событие для Worker'а пишется в той же транзакции, что и смена статуса бита; relay публикует его раз в секунду с подтверждением брокера.
- **Повторы:** 30 с / 2 мин / 10 мин через очереди задержки, затем DLQ; обработчики идемпотентны.
- **Платёж:** `capture: false`, `Idempotence-Key`, вебхук сверяется запросом статуса и обрабатывается один раз; `capture`/`cancel` — после коммита, зависшие холды доводит планировщик.

## Чего здесь нет — сознательно

- Вне MVP (по документации): возвраты и споры, отмена заказа покупателем, докачка больших файлов, мультивалютность, мобильные приложения, рекомендации.
- Только локальный запуск: нет HTTPS и TLS (NFR-6), размещения в РФ (NFR-30), SLA (NFR-12…14), нагрузки 1000 RPS (NFR-2). Код им не мешает.
- Внешние сервисы — моки, и это постоянная часть проекта: ЮKassa (`yookassa_mock/`), SMS и email (лог и «входящие»), антивирус (тестовая сигнатура EICAR, режим «недоступен»). Тексты договора и оферты — заглушки до юридической проверки (GAP-31).

## Остановка и данные

- `docker compose stop` — остановить, всё сохранится.
- `docker compose down` — удалить контейнеры; данные в томах сохранятся, `docker compose up` вернёт всё как было.
- `docker compose down -v` — **удалить и данные** (база, файлы, платежи мока). Только если хотите начать с чистого листа.
