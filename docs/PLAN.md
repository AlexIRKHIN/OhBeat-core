## 1. Как я понял продукт и архитектуру

OhBeat — маркетплейс битов. Продюсер подключается к продажам и загружает мастер WAV, стемы и обложку с ценами на четыре лицензии. Артист слушает превью с войстегом платформы, покупает лицензию, получает договор с простой электронной подписью и скачивает файлы по ссылкам, которые живут час. Тяжёлые файлы идут из браузера прямо в S3 и обратно, минуя сервер. Core API — модульный монолит: он работает с метаданными, выдаёт подписанные ссылки и отвечает за деньги, права и договоры. Тяжёлую обработку аудио делает отдельный Media Worker: он слушает RabbitMQ и не имеет доступа к БД, а команды до него доходят без потерь благодаря transactional outbox. Эксклюзив не продаётся дважды: на него ставится атомарный резерв на 15 минут, а при холдировании денег бит проверяется ещё раз. Двухстадийный платёж ЮKassa со сплитованием позволяет отменить холд без списания, а при успехе сразу делит деньги между Продюсерами и комиссией платформы, начисленной сверх цены.

## 4. Этапы работы (вертикальные срезы)

Сложность: **M** — 1–3 дня, **L** — 3–5 дней, **XL** — больше недели работы. Оценки относительные.

Сквозные вещи, которые появляются в срезе 0 и дальше только расширяются: единый формат ошибок, проверка прав на каждом эндпоинте (роль, владелец бита, владелец заказа), запись в `audit_log`, русский и английский интерфейс (NFR-26), даты ДД.ММ.ГГГГ ЧЧ:ММ по Москве (NFR-28, NFR-29), рубли со знаком ₽ (NFR-27), адаптивная вёрстка от 320×568 (NFR-9, NFR-21), toast при потере связи (NFR-19), состояния «загрузка / ошибка / пусто / нет связи» на каждом экране.

### Срез 1. Публикация бита и «Мои биты» — **XL**

**Что получится.** Форма загрузки со всеми правилами из UI-спецификации §1 и критериями AC-1…AC-5. 3. Выбрать MP3 в зону WAV → красный алерт, загрузка не стартует.
4. Во время загрузки включить в DevTools режим Offline → toast и «Повторить».
5. RabbitMQ UI (`http://localhost:15672`): видно очереди и сообщения. MinIO Console (`http://localhost:9001`): файлы разложены по бакетам.

### Срез 3. Покупка: корзина → заказ → резерв → платёж со сплитованием → вебхук → выдача — **XL**

Самый рискованный срез. Предлагаю делать его тремя частями, с коммитами и коротким показом после каждой.

**3a. Корзина и заказ.** Корзина с ценами Продюсеров, строкой комиссии и итогом (FR-15). `POST /orders`: сверка `expected_price`, проверка данных покупателя, снимок в `billing_snapshot` (GAP-8), фиксация цены и комиссии по позициям, атомарный резерв Exclusive, договор-акцепт для остальных лицензий (GAP-30). Планировщик FR-29 — оба запроса из `Database_Schema.md` §6.

**3b. Платёж и вебхук.** `POST /orders/{id}/payments`: `capture: false`, `transfers` по Продюсерам (GAP-41), `Idempotence-Key`, 3 повтора, `503` при недоступности. Вебхук: проверка IP (выключена настройкой), сверка `GET /v3/payments/{id}`, одна транзакция «событие + статусы», `200` после коммита. Решение по FR-23 → `capture` или `cancel` после коммита, с фоновым доведением (GAP-35). FR-24 (включая `expired` → `paid`), FR-25.

**3c. Выдача.** PDF договоров с хэшем `pdf_sha256` (GAP-43), страница возврата с опросом каждые 2 с до 60 с, «Мои покупки», `GET /orders/{id}/downloads` со ссылками на час, письма (мок).

| | |
| --- | --- |
| FR | FR-14 … FR-30 (кроме OTP-части FR-16 — она в срезе 4) |
| NFR | NFR-7, NFR-8, NFR-25, NFR-27, NFR-29 |
| Эндпоинты | `GET /cart`, `PUT/DELETE /cart/items/{beat_id}`, `POST /orders`, `GET /orders/{id}`, `POST /orders/{id}/payments`, `POST /payments/webhook`, `GET /orders/{id}/downloads`, `GET /users/me/purchases`; `GET /users/me/sales` — статистика продаж FR-34 (если перенос одобрен) |
| Таблицы | `cart_items`, `orders`, `order_items`, `payments`, `payment_events`, `contracts`, `beats`, `audit_log` |

**Путь (по `sequence_exclusive_purchase.png`):** `POST /orders` → одна транзакция: `orders` + `order_items` + `UPDATE beats … WHERE status = 'active'` → `POST /payments` → ЮKassa (мок) → редирект на страницу оплаты мока → вебхук `waiting_for_capture` → сверка → транзакция: `payment_events` + `beats.status = sold` → `capture` → вебхук `succeeded` → `orders.status = paid` + PDF + `audit_log` → опрос `GET /orders/{id}` → ссылки.

**Обязательные тесты:**

- **Гонка двух покупателей за один Exclusive:** параллельные транзакции на настоящем PostgreSQL — ровно один `201`, остальные `409 BEAT_RESERVED`.
- **Повторный вебхук:** одно событие 2–5 раз, в том числе одновременно → одна обработка, на каждый ответ `200`.
- **Истёкший резерв при приходе `waiting_for_capture`:** бит свободен → `capture`; занят другим заказом → `cancel`, заказ `canceled`; уже `sold` → `cancel`.
- **Оплата после `expired`:** проверка прошла → `expired` → `paid`; не прошла → `canceled`.
- **Сумма `transfers` и комиссии:** Σ `transfers` + Σ `platform_fee` = сумма платежа до копейки; заказ с битами двух Продюсеров.
- Таймаут ЮKassa → 3 повтора с одним ключом → `503`, резерв сохранён.
- Падение между коммитом вебхука и `capture` → фоновая задача доводит платёж (GAP-35).
- Окончательный сбой `capture` → бит снова `active` (FR-23).
- Чужой заказ → `403`; неоплаченный → `409 ORDER_NOT_PAID`; ссылка живёт не дольше 3600 с.

**Как проверить руками.** Для демонстрации сроки можно сократить в `.env` (резерв — 2 минуты, ссылки — 1 минута).

1. Купить Basic: корзина (цена, комиссия, итог) → оферта → страница мока ЮKassa → карта «успех» → ссылки на MP3 и договор.
2. Два браузера, два пользователя одновременно оформляют один Exclusive → у одного сообщение «Этот эксклюзив прямо сейчас оформляет другой покупатель».
3. На странице мока карта «отказ банка» → заказ остаётся `pending`, оплату можно повторить.
4. В пульте мока «Повторить вебхук» → в логах видно, что дубликат отсеян.
5. Дать резерву истечь и оплатить «с опозданием» → списание проходит, если бит никто не занял.
6. В пульте мока посмотреть распределение: сколько ушло каждому Продюсеру, сколько осталось платформе.

**Что получится.** Для заказа с Exclusive: просмотр проекта договора → «Подписать» → код по SMS (мок пишет в лог) → ввод кода → подпись зафиксирована. Без подписи `POST /orders/{id}/payments` → `428 SIGNATURE_REQUIRED`. Итоговый PDF со штампом ПЭП по RFC §5.

**Как проверить руками.** Оформить Exclusive, найти код командой `docker compose logs api | grep OTP`, трижды ввести неверный код, запросить новый, подписать, оплатить. Сверить штамп и хэш в PDF с «Моими покупками».

**Как проверить руками.** Отправить бит в DLQ (мок-антивирус в режиме «недоступен») → бит появляется в списке застрявших → «Повторить» с выключенным сбоем → бит опубликован. Удалить используемый жанр → `409 GENRE_IN_USE`. Найти в Audit Log оба действия.

### Финал. Сквозная проверка и запуск с нуля — **M**

- Сквозной автотест в браузере: регистрация → подключение к продажам → публикация → каталог → покупка Basic и Exclusive с OTP → договор → скачивание.
- Запуск с нуля одной командой (`docker compose up --build`): миграции, сиды, образцы файлов.
- README: что это за продукт, как запустить, демо-аккаунты, адреса консолей, сценарии ручной проверки, ссылки на ADR и GAPS.

## 6. Риски и сложные места

1. **Вебхук и внешние вызовы.** Решение принимается в транзакции, а `capture`/`cancel` — сетевой вызов после неё. Без фонового доведения платёж может зависнуть в холде (GAP-35).
2. **Гонки:** параллельные заказы на один Exclusive; вебхук против планировщика (резерв истекает ровно в момент оплаты); два одинаковых вебхука одновременно. Проверяется только тестами на настоящем PostgreSQL с параллельными соединениями.
3. **`Idempotence-Key` и `NOT NULL provider_payment_id`** (GAP-6): ключ нельзя сохранить до ответа ЮKassa, поэтому повторы живут в памяти.
4. **Хост в presigned-ссылках:** Core API ходит в MinIO по внутреннему адресу, а браузеру нужен `localhost:9000`. Подпись включает хост, поэтому ссылки подписываются с публичным адресом.
5. **Повторная доставка сообщений:** relay может отправить событие дважды, Worker — обработать дважды. Защита — детерминированные ключи файлов и условие `WHERE status = 'processing'`.
6. **Деньги:** `NUMERIC`/`Decimal` везде; округление комиссии (GAP-42); равенство суммы платежа и `transfers`; сверка суммы во вебхуке.
7. **Договоры:** неизменность проекта между кодом и PDF держится на снимке данных обеих сторон (GAP-8, GAP-9). Ошибка здесь сделает `draft_sha256` бессмысленным.
8. **Время:** в БД UTC, в интерфейсе и договорах Москва. Резерв, OTP и ссылки зависят от времени, поэтому в тестах подменяем часы, а не ждём 15 минут.
9. **Права в БД:** миграции и приложение работают под разными ролями. Если перепутать, NFR-32 молча перестанет действовать. Покрыто тестом.
10. **FFmpeg:** войстег с интервалом, правильная длительность; ошибки на битых файлах нужно отличать от временных сбоев (отклонение против повтора).
11. **Объём интерфейса:** 37 FR, три роли, два языка, все состояния. Основной риск по срокам. Держим единые компоненты форм и состояний.

## 7. Пробелы и противоречия

Все найденные — в [GAPS.md](GAPS.md): 45 записей, из них 4 уже решены вашими ответами. Самые важные:

- **GAP-6** — `Idempotence-Key` нельзя сохранить в `payments` до ответа ЮKassa: `provider_payment_id NOT NULL`.
- **GAP-35 / GAP-36** — `capture`/`cancel` после коммита вебхука могут потеряться; порядок смены статуса заказа на диаграмме и в REST различается.
- **GAP-8 / GAP-9** — данные Продюсера не попадают в снимок заказа, а `draft_sha256` негде хранить между отправкой и проверкой кода.
- **GAP-2** — логическая и физическая модели расходятся в кратности «позиция → договор».
- **GAP-21 / GAP-22** — как найти «застрявший» бит и что делать, если исходники уже удалены lifecycle-правилом.
- **GAP-31** — нет юридического текста договора.

Ни одно из этих допущений не блокирует срез 0.
