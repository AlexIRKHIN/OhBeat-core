## 1. Как я понял продукт и архитектуру

OhBeat — маркетплейс битов. Продюсер загружает мастер WAV, стемы и обложку и задаёт цены на четыре лицензии. Артист слушает превью с войстегом, покупает лицензию, получает договор с простой электронной подписью и скачивает файлы по ссылкам, которые живут час. Тяжёлые файлы идут из браузера прямо в S3 и обратно, минуя сервер. Core API (модульный монолит) работает только с метаданными, выдаёт подписанные ссылки и отвечает за деньги и права. Тяжёлую обработку аудио (проверка, MP3, войстег) делает отдельный Media Worker. Он слушает RabbitMQ и не имеет доступа к БД, а команды до него доходят без потерь благодаря transactional outbox. Главные инварианты держит PostgreSQL. Эксклюзив не продаётся дважды благодаря атомарному резерву на 15 минут и повторной проверке в момент холдирования денег. Двухстадийный платёж ЮKassa позволяет отменить холд без списания, если бит уже ушёл другому покупателю.

## 2. Выбор стека

Документация не фиксирует язык, фреймворки, миграции, генерацию PDF и тесты. Вы выбрали Python, поэтому оба варианта — на Python. Фронтенд в обоих вариантах — SPA (этого требует архитектура).

### Вариант A — FastAPI + SQLAlchemy + Alembic, фронтенд React (рекомендую)

| Слой | Технология |
| --- | --- |
| Core API | Python 3.12, FastAPI, Pydantic v2, SQLAlchemy 2.0 (синхронный, psycopg 3) |
| Миграции | Alembic, миграции написаны **на чистом SQL**, один в один как в `Database_Schema.md` |
| Брокер | `pika` (RabbitMQ: publisher confirms, delay-очереди, DLQ — топология настраивается вручную) |
| Фоновые процессы | Outbox relay, планировщик (APScheduler), обработчик результатов Worker'а — отдельные процессы из той же кодовой базы |
| Media Worker | Python + FFmpeg 6 / ffprobe в docker-образе (Debian) |
| PDF | WeasyPrint (HTML-шаблон → PDF, кириллица, штамп ПЭП в рамке) |
| Фронтенд | React 18 + TypeScript + Vite, TanStack Query, React Hook Form + Zod, react-i18next |
| Тесты | pytest на настоящих PostgreSQL, RabbitMQ и MinIO (в docker), Vitest для фронтенда, Playwright для сквозного сценария |

**Плюсы для OhBeat:**

- Полный контроль над SQL: `GENERATED ALWAYS AS IDENTITY`, `CHECK`, частичные индексы, `REVOKE UPDATE, DELETE` на `audit_log`, атомарный `UPDATE … WHERE status = 'active' RETURNING` — всё пишется ровно так, как в документации.
- Транзакции явные. Резерв, вебхук и outbox видны в коде как отдельные блоки, и их легко сверить с FR-18, FR-23 и FR-29.
- FastAPI сам генерирует Swagger (`/docs`) из кода. Вы сможете сверять живые контракты с `REST_API_Contracts.md` без чтения кода. Для аналитика это сильный плюс.
- Pydantic даёт серверную валидацию и единый формат ошибок `error_code / message / details` в одном месте.
- React + Zod: правила валидации формы описываются одной схемой, а кнопка «Опубликовать» неактивна, пока схема не пройдёт (FR-3, NFR-11).

**Минусы:**

- Админку придётся писать самим: это небольшой отдельный срез.
- Больше «ручной» обвязки: авторизация, зависимости, структура модулей.
- Два языка в проекте (Python и TypeScript).

### Вариант B — Django + Django REST Framework, фронтенд Vue 3

| Слой | Технология |
| --- | --- |
| Core API | Django 5, DRF |
| Миграции | Django migrations + `RunSQL` для того, что ORM не умеет |
| Брокер, Worker, PDF, тесты | Те же `pika`, FFmpeg, WeasyPrint, pytest-django, Playwright |
| Админка | Встроенная Django Admin |
| Фронтенд | Vue 3 + TypeScript + Vite, Pinia, vue-i18n, VeeValidate |

**Плюсы:**

- Встроенная админка почти бесплатно: справочники, просмотр `audit_log`.
- Много готового: пользователи, хэширование паролей, валидаторы.
- Vue немного проще читать неразработчику.

**Минусы:**

- ORM генерирует схему сам. Django создаёт `GENERATED BY DEFAULT AS IDENTITY`, а не `ALWAYS`, имена ограничений свои. Чтобы схема совпала с документом, придётся постоянно обходить ORM через `RunSQL`, и миграции разойдутся с моделями.
- Встроенный `User` Django плохо ложится на схему (`users` + `user_roles` + `profiles`). Придётся заменять его своим, а это известный источник сложностей.
- Django Admin по умолчанию хочет права на изменение. Для `audit_log` без `UPDATE`/`DELETE` нужна аккуратная настройка, иначе админка упадёт с ошибкой прав.
- Swagger не встроен (нужен drf-spectacular), и схема в нём менее точная.
- Резерв и вебхук всё равно пишутся на сыром SQL, то есть главное преимущество ORM здесь не работает.

### Рекомендация

**Вариант A.** В OhBeat самое ценное — точное следование схеме БД и транзакционной логике из документации. FastAPI + SQL-миграции не мешают этому, а Django мешает. Встроенная админка Django экономит дни, но нам нужна лишь маленькая админка (три экрана), поэтому эта экономия не окупает борьбу с ORM.

## 3. Этапы работы (вертикальные срезы)

Сложность: **S** — до дня, **M** — 1–3 дня, **L** — 3–5 дней, **XL** — больше недели работы. Оценки относительные. После каждого среза — таблица «требование → код → тест», инструкция для ручной проверки и остановка.

Сквозные вещи, которые делаются с первого среза и дальше только расширяются: единый формат ошибок, i18n (ru/en, NFR-26), формат дат ДД.ММ.ГГГГ ЧЧ:ММ по Москве (NFR-28, NFR-29), адаптивная вёрстка от 320×568 (NFR-9, NFR-21), toast при потере связи (NFR-19), запись в `audit_log`, проверка прав на каждом эндпоинте.

### Срез 1. Публикация бита — сложность **XL**

**Что получится:** продюсер заполняет форму (все правила из UI-спецификации §1 и AC-1…AC-5), файлы параллельно грузятся прямо в MinIO с прогресс-барами и кнопкой «Повторить». Затем идёт `confirm` → outbox → RabbitMQ → Worker (ffprobe, проверка ZIP, мок-антивирус, проверка обложки, MP3 320, превью 128 с войстегом каждые 20 с, перенос по бакетам) → результат → бит `active` или `rejected` с причиной. Готовы «Мои биты» со статусами, редактирование цен, скрытие и удаление с подтверждением.

| | |
| --- | --- |
| FR | FR-1 … FR-13 |
| NFR | NFR-3, NFR-10, NFR-11, NFR-17, NFR-19, NFR-20, NFR-22 |
| Эндпоинты | `POST /beats`, `POST /beats/{id}/uploads` (GAP-16), `POST /beats/{id}/confirm`, `GET /me/beats`, `GET /beats/{id}`, `PUT /beats/{id}/licenses/{code}`, `PATCH /beats/{id}`, `DELETE /beats/{id}` |
| Очереди | `media.events`, `beat_processing_queue`, `beat_results_queue`, 3 очереди задержки, `beat_processing_dlq`, `beat_results_dlq` |
| Таблицы | `beats`, `beat_files`, `beat_genres`, `beat_prices`, `genres`, `licenses`, `outbox`, `audit_log`; новая `stop_words` (GAP-12) |
| Фон | outbox relay (раз в секунду, `FOR UPDATE SKIP LOCKED`), потребитель результатов, планировщик: `uploading` дольше 24 ч → `deleted` (FR-8) |

**Обязательные тесты:** повторная доставка `beat.media.process` и `beat.media.processed` (бит меняется ровно один раз); падение relay между публикацией и отметкой `published_at`; временная ошибка S3 → повторы 30 с / 2 мин / 10 мин → DLQ; `confirm` без файла → `422 FILES_MISSING`; MinIO отклоняет файл больше лимита из политики; Worker отклоняет MP3, переименованный в `.wav`, WAV длиннее 10 минут, ZIP с `.exe`, ZIP с EICAR, обложку 3:2.

**Как проверить руками:** в репозитории будет папка `samples/` с хорошими и плохими файлами.

1. Загрузить хороший бит → «Бит загружен и обрабатывается» → через несколько секунд в «Моих битах» статус «Опубликован».
2. Загрузить ZIP с `readme.exe` → статус «Отклонён» с причиной.
3. Выбрать MP3 в зону WAV → красный алерт, загрузка не стартует.
4. Во время загрузки выключить сеть (DevTools → Offline) → toast и «Повторить».
5. RabbitMQ UI `http://localhost:15672` — видно очереди и сообщения; MinIO Console `http://localhost:9001` — файлы разложены по бакетам.
6. Скачать превью из MinIO и послушать войстег.

### Срез 2. Каталог и стриминг превью — сложность **M**

**Что получится:** публичный каталог с фильтрами (жанр, BPM от–до, тональность, максимальная цена), поиском, сортировкой и курсорной пагинацией. Один общий плеер на странице: `preload="none"`, при переключении трека — `pause()` + `removeAttribute('src')` + `load()`. Страница бита и публичная страница продюсера. Метка «В резерве».

| | |
| --- | --- |
| FR / US | FR-19 (метка в каталоге), US-A1, US-A2, US-P5 (витрина), UC-1 … UC-3 |
| NFR | NFR-1, NFR-9, NFR-21, NFR-27, NFR-28; `RFC_Audio_Streaming.md` |
| Эндпоинты | `GET /beats`, `GET /beats/{id}`, `GET /producers/{id}` |

Worker при загрузке превью ставит `Cache-Control: public, max-age=31536000, immutable` и `Content-Type: audio/mpeg`. В ответ API попадают публичные URL MinIO с хостом, доступным из браузера (`localhost:9000`), а не внутренний `minio:9000`.

**Тесты:** `price_max` считается по минимальной активной цене; курсор стабилен при добавлении новых битов; `reserved` виден с `is_reserved: true`; `sold`, `hidden`, `deleted` не видны; интеграционный тест на `206 Partial Content` с `Content-Range`.

**Как проверить руками:**

1. Каталог фильтруется, при отсутствии результатов показано состояние «Ничего не найдено».
2. DevTools → Network: до Play запросов к MP3 нет; при Play и перемотке видны ответы `206`.
3. `curl -I -H "Range: bytes=1000-" http://localhost:9000/public-media/previews/<id>_v1.mp3` → `206`.
4. Сузить окно до 320 px — вёрстка не ломается.

### Срез 3. Покупка: корзина → заказ → резерв → платёж → вебхук → выдача — сложность **XL**

Это самый рискованный срез. Предлагаю делать его тремя частями, с коммитами и коротким показом после каждой.

**3a. Корзина, данные покупателя, заказ, резерв.** Корзина (одна лицензия на бит, замена лицензии, пересчёт суммы), форма «Данные покупателя» (UI-спецификация §2: маски, ИНН с контрольной суммой, 8 → +7), `POST /orders` с атомарным резервом, `PRICE_CHANGED`, отмена заказа, планировщик снятия резервов (с исправленным SQL, GAP-38) и истечения заказов без резерва (GAP-35).

**3b. Платёж и вебхук.** `POST /orders/{id}/payments` (`capture: false`, `Idempotence-Key` из `payments`, 3 повтора), вебхук: проверка IP (выключена настройкой), сверка `GET /v3/payments/{id}`, дедупликация в `payment_events`, проверка FR-23 → capture или cancel через фоновый обработчик с повторами, `succeeded` → `paid`, `canceled` по FR-25.

**3c. Выдача.** PDF договоров (оферта для Basic/Premium/Trackout) с хэшем `pdf_sha256`, страница возврата с опросом каждые 2 с до 60 с, «Мои покупки», `GET /orders/{id}/downloads` со ссылками на 1 час, письмо (мок).

| | |
| --- | --- |
| FR | FR-14 … FR-29 (кроме OTP-части FR-16 — она в срезе 4) |
| NFR | NFR-7, NFR-8, NFR-11, NFR-27, NFR-29 |
| Эндпоинты | `GET /cart`, `PUT/DELETE /cart/items/{beat_id}`, `GET/PUT /users/me/billing`, `POST /orders`, `GET /orders/{id}`, `POST /orders/{id}/cancel`, `POST /orders/{id}/payments`, `POST /payments/webhook`, `GET /orders/{id}/downloads`, `GET /me/purchases` |
| Таблицы | `cart_items`, `orders`, `order_items`, `payments`, `payment_events`, `contracts`, `beats`, `audit_log`, `outbox`; новая `billing_profiles` (GAP-32) |

**Обязательные тесты:**

- **Гонка двух покупателей за один Exclusive:** N параллельных транзакций на настоящем PostgreSQL — ровно один `201`, остальные `409 BEAT_RESERVED`.
- **Повторный вебхук:** то же событие 2–5 раз, в том числе параллельно → один capture, один переход в `paid`, на каждый ответ `200`.
- **Истёкший резерв при приходе `waiting_for_capture`:** (а) бит свободен (`active`) → capture и `sold`; (б) бит занят другим заказом → cancel, заказ `canceled`; (в) бит уже `sold` → cancel.
- Таймаут ЮKassa при создании платежа → 3 повтора с одним ключом → «Платёжный сервис временно недоступен», резерв сохранён.
- Сумма в ЮKassa не совпала с заказом → cancel (GAP-42).
- Capture окончательно не прошёл → бит снова `active` (FR-23).
- SQL планировщика: заказ действительно уходит в `expired` (GAP-38).
- Чужой заказ → `403`, неоплаченный → `409 ORDER_NOT_PAID`, ссылка живёт не дольше 3600 с.

**Как проверить руками:** для демонстрации срок резерва можно сократить в `.env` (например, `RESERVATION_TTL=2m`).

1. Купить Basic: корзина → данные покупателя → оферта → страница мок-ЮKassa → карта «успех» → возврат → ссылки на MP3 и договор.
2. Два браузера (обычный и инкогнито), два пользователя одновременно жмут «Оформить» на один Exclusive → у одного сообщение «Этот эксклюзив прямо сейчас оформляет другой покупатель».
3. На странице мока выбрать карту «отказ банка» → заказ остаётся `pending`, можно оплатить снова.
4. В пульте мока нажать «Повторить вебхук» → в логах видно, что событие отсеяно как дубликат.
5. Подождать истечения резерва и оплатить «с опозданием» → списание проходит, если бит никто не занял.
6. Открыть ссылку на скачивание через час (или с `DOWNLOAD_TTL=1m`) → доступ запрещён.

### Срез 4. Подпись Exclusive по OTP — сложность **M**

**Что получится:** для заказа с Exclusive — просмотр проекта договора, «Подписать» → код по SMS или email (мок пишет код в лог) → ввод кода → подпись зафиксирована. Без подписи `POST /orders/{id}/payments` → `428 SIGNATURE_REQUIRED`. Итоговый PDF со штампом ПЭП по RFC §5.

| | |
| --- | --- |
| FR | FR-16 (Exclusive), FR-17, FR-26 (штамп) |
| NFR | NFR-7, NFR-31; `RFC_Digital_Signature.md` |
| Эндпоинты | `GET /orders/{id}/contract-draft` (GAP-48), `POST /orders/{id}/signature/otp`, `POST /orders/{id}/signature/verify` |
| Таблицы | `signature_otps` (+ `draft_sha256`, GAP-47), `contracts`, `audit_log` |

**Тесты:** 3 неверные попытки → блок; код живёт 5 минут (подменяем часы); повторная отправка не раньше 60 с; не больше 5 отправок в час на пользователя; в БД только хэш (HMAC-SHA256 с секретом); код нельзя использовать дважды; подпись после истечения резерва → `410`; хэш проекта в штампе совпадает с `contracts.draft_sha256`, хэш файла — с `pdf_sha256`.

**Как проверить руками:** купить Exclusive, найти код командой `docker compose logs api | grep OTP`, ввести неверный код 3 раза, потом запросить новый, подписать, оплатить. Открыть PDF и сверить штамп и хэш с «Моими покупками».

### Срез 5. Комиссия и выплаты продюсерам — сложность **M**

**Что получится:** при создании платежа в ЮKassa уходят `transfers` по каждой позиции (сплит, NFR-25). Комиссия фиксируется в `order_items.platform_fee`. После `succeeded` мок проводит перечисления, их статусы видны в «Моих продажах» у продюсера (UC-14).

| | |
| --- | --- |
| FR | FR-30 |
| NFR | NFR-25, NFR-27 |
| Эндпоинты | `GET /me/sales`; реквизиты выплат в `POST/PUT /users/me/producer` |
| Таблицы | `order_items.platform_fee`, `producer_accounts.payout_token`; новая `payouts` (GAP-54) |

**Тесты:** сумма комиссий и перечислений до копейки равна сумме заказа; заказ с битами трёх продюсеров; неудачное перечисление → повтор без дублей.

**Как проверить руками:** купить корзину с битами двух продюсеров, затем войти за каждого и посмотреть «Мои продажи»: сумма, комиссия, статус перечисления.

### Срез 6. Минимальная админка — сложность **S–M**

Audit Log с фильтрами (только чтение), справочники жанров и стоп-слов, список битов, застрявших в `processing`, с действиями «Повторить» и «Отклонить» (GAP-21). Эндпоинты `/admin/*`, только для роли `admin`. Админ создаётся сидом.

### Срез 7. Сквозная проверка и запуск с нуля — сложность **M**

- Сквозной автотест Playwright: публикация → каталог → покупка Basic и Exclusive с OTP → договор → скачивание.
- Запуск с нуля одной командой (`docker compose up --build`): миграции, сиды (жанры, лицензии, стоп-слова, демо-продюсер с битами, демо-артист, админ) и образцы файлов.
- README: что это за продукт, как запустить, демо-аккаунты, адреса консолей, сценарии ручной проверки, ссылки на ADR и GAPS.

### Порядок и общая оценка

0 → 1 → 2 → 3a → 3b → 3c → 4 → 5 → 6 → 7. Суммарно это несколько недель работы. Самые тяжёлые срезы — 1 и 3.

## 4. Моки

Все внешние сервисы спрятаны за интерфейсами (`PaymentGateway`, `Notifier`, `AntivirusScanner`, `ObjectStorage`). Моки — постоянная часть проекта.

| Мок | Что эмулирует | Неудачные сценарии |
| --- | --- | --- |
| **ЮKassa** (отдельный контейнер `yookassa-mock`) | `POST /v3/payments` с семантикой `Idempotence-Key` (тот же ключ → тот же платёж), `GET /v3/payments/{id}`, `POST …/capture`, `POST …/cancel`; `confirmation_url` ведёт на страницу оплаты мока; вебхуки `payment.waiting_for_capture`, `payment.succeeded`, `payment.canceled` в Core API; `transfers` (сплит) и перечисления продюсерам (срез 5); автоотмена холда по таймауту | Тестовые карты на странице оплаты: успех, отказ банка (`canceled` с `cancellation_details`), «холд без вебхука»; пульт управления (страница и API): повторить вебхук N раз, задержать вебхук, отправить вебхуки в обратном порядке, следующий запрос → таймаут / 500 / 429, сбой capture, сбой перечисления |
| **SMS / Email** (`Notifier` внутри Core API) | Отправка OTP и транзакционных писем: публикация и отклонение бита, продажа, оплата | Пишет структурированную строку в лог (`OTP sent: order=…, code=…`); по настройке может «падать», чтобы проверить ошибку отправки |
| **Антивирус** (`AntivirusScanner` внутри Worker) | Проверка содержимого ZIP | Находит «вирус» по сигнатуре EICAR в любом файле архива; по настройке эмулирует недоступность сканера (временная ошибка → повторы через очередь задержки) |
| **S3** | Не мок: настоящий MinIO (S3-совместимый): presigned POST с `content-length-range`, `HeadObject`, presigned GET, lifecycle, Range-запросы | Временную недоступность S3 эмулируем в тестах остановкой контейнера или подменой клиента |
| **CDN** | Не нужен: превью и обложки отдаёт публичный бакет MinIO | — |

Проверка IP-адресов ЮKassa на вебхуке реализована и выключена настройкой `YOOKASSA_IP_CHECK=false`.

## 5. Риски и сложные места

1. **Вебхук: «200 сразу» против «обработать ровно один раз»** (GAP-40). Если сохранить событие до обработки, сбой обработки потеряет его навсегда. Решение: сверка → одна транзакция «событие + статусы + задача на capture в outbox», а сетевые вызовы capture/cancel — вне транзакции, с повторами.
2. **Ошибка в SQL снятия резервов** (GAP-38): если скопировать запрос из документации буквально, заказы не будут истекать. Покрыто тестом.
3. **Гонки:** параллельные заказы на один Exclusive; вебхук против планировщика (резерв истекает ровно в момент `waiting_for_capture`); два одинаковых вебхука одновременно. Нужны правильные условия в `UPDATE`, блокировки строк и тесты на настоящем PostgreSQL с параллельными соединениями.
4. **Хост в presigned-ссылках:** Core API ходит в MinIO по адресу `minio:9000`, а браузеру нужен `localhost:9000`. Подпись включает хост, поэтому ссылки подписываются отдельным клиентом с публичным адресом. CORS на бакете нужен для загрузки из браузера.
5. **Presigned POST и большие файлы:** ZIP до 1 ГБ через браузер, прогресс и обрыв. Докачки нет (вне MVP), поэтому «Повторить» начинает файл заново, а политики могут истечь (GAP-16).
6. **Повторная доставка сообщений:** relay может отправить событие дважды, Worker может обработать команду дважды. Идемпотентность держится на детерминированных ключах и условии `WHERE status = 'processing'`.
7. **Деньги:** `NUMERIC` и `Decimal` везде, никаких `float`; копейки при делении комиссии между позициями; сверка суммы платежа с заказом.
8. **Часы и часовые пояса:** в БД UTC, в интерфейсе и договорах Москва. Резерв, OTP и ссылки зависят от времени, поэтому в тестах подменяем часы, а не ждём 15 минут.
9. **OTP:** хранить только хэш, честно считать лимиты (60 с, 5 в час, 3 попытки) при параллельных запросах, не раскрывать код в ответах API.
10. **`audit_log` только на добавление:** миграции и приложение работают под разными ролями. Если перепутать, ограничение NFR-32 молча перестанет действовать. Покрыто тестом.
11. **FFmpeg:** наложение войстега с интервалом и нормализацией громкости, корректная длительность, MP3 с правильным `Content-Type`. Ошибки FFmpeg на битых файлах нужно отличать от временных сбоев (отклонение против повтора).
12. **Объём интерфейса:** экранов много, и большинство не описано (GAP-28). Это основной риск по срокам. Держим единые компоненты: формы, состояния, toast.
13. **Docker на Windows:** MinIO и PostgreSQL на томах Docker Desktop работают нормально, но FFmpeg на больших WAV медленнее. Для демо подойдут файлы на 2–4 минуты.

## 6. Пробелы и противоречия

Все найденные — в [GAPS.md](GAPS.md): 58 записей. Самые важные для вашего решения:

- **GAP-38** — ошибка в SQL снятия резервов (`RETURNING` возвращает уже `NULL`).
- **GAP-40** — порядок «сохранить событие → ответить 200» конфликтует с гарантией обработки.
- **GAP-54 / GAP-55** — FR-30 и NFR-25 описывают разные механизмы выплат; размер комиссии не задан.
- **GAP-36** — когда заказ становится `canceled`: диаграмма и FR-25 расходятся, эндпоинта отмены нет.
- **GAP-20** — «3 попытки» против трёх очередей задержки.
- **GAP-34** — обязателен ли телефон для Exclusive (UI против RFC).
- **GAP-1, 2, 27, 28, 30, 32** — недостающие эндпоинты, таблицы и экраны (регистрация, refresh-токены, корзина, данные покупателя, «Мои …»).
- **GAP-50** — нет юридического текста договора и условий лицензий.
