# ADR 0001. Бэкенд: Python, FastAPI, SQLAlchemy 2

Дата: 31.10.2026. Статус: принято.

## Контекст

Документация задаёт архитектуру (модульный монолит Core API + Media Worker + планировщик) и схему БД (`schema.sql`), но не язык и фреймворк. Аналитик предпочёл Python. Важнее всего — буквально повторить схему и транзакционную логику: резерв (FR-18), вебхук (FR-22…FR-25), планировщик (FR-29).

## Варианты

- **FastAPI + SQLAlchemy 2.** Полный контроль над SQL и транзакциями, Swagger генерируется из кода, валидация на Pydantic. Минус: авторизацию и структуру модулей пишем сами.
- **Django + DRF.** Много готового, но ORM хочет сам владеть схемой (`BY DEFAULT` вместо `ALWAYS` в identity, свои имена ограничений), встроенный `User` не ложится на `users` + `user_roles` + `profiles`, а встроенная админка не нужна: интерфейс Администратора по архитектуре входит в SPA.

## Решение

Python 3.12, FastAPI, Pydantic v2, SQLAlchemy 2 в синхронном режиме с драйвером psycopg 3. Критичные запросы (резерв, продажа, планировщик) пишутся явным SQL в явных транзакциях. RabbitMQ — библиотека `pika`. Media Worker — тоже Python, FFmpeg вызывается как внешняя программа.

## Последствия

- Swagger по адресу `/docs` позволяет сверять живые контракты с `REST_API_Contracts.md`.
- Синхронный код проще читать; запросы FastAPI выполняет в пуле потоков, для локального MVP этого достаточно.
- Модули Core API (`auth`, `users`, `catalog`, `orders`, `payments`, `contracts`, `admin`, `notifications`) разделены пакетами с явными границами.
