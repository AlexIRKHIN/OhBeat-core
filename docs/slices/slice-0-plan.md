# Срез 0. Каркас, учётные записи, подключение к продажам — план

Статус: **ждёт «ок» аналитика**. Общий план — [PLAN.md](../PLAN.md), стек — [ADR](../adr/README.md).

## 1. Что получится

После `docker compose up` в браузере открывается OhBeat. Можно зарегистрироваться с согласиями, войти и выйти, заполнить профиль с аватаром и «Данные покупателя», подключиться к продажам и получить роль Продюсера. Каталога и загрузки битов ещё нет — на их месте заглушки «появится в срезе 1/2».

## 2. Требования

| Требование | Что делаем |
| --- | --- |
| FR-31 | Регистрация по email и паролю, обязательные согласие на обработку ПД и соглашение о ПЭП, роль Артиста, запись в Audit Log |
| FR-32 | Профиль (имя, описание, аватар) и форма «Данные покупателя» |
| FR-33 | Подключение к продажам: проверка данных для договора, налоговый статус, `yookassa_account_id`, соглашения → роль Продюсера |
| NFR-4 | Пароль хранится как хэш Argon2id (соль внутри хэша) |
| NFR-5 | ≥ 8 символов, заглавная латинская, цифра, спецсимвол — на клиенте и на сервере |
| NFR-22 | Аватар: PNG/JPG/WebP, ≤ 5 МБ, ≤ 2048×2048 |
| NFR-26, 28, 29 | Русский и английский интерфейс, даты ДД.ММ.ГГГГ ЧЧ:ММ по Москве |
| NFR-30 | Согласие на обработку ПД при регистрации (`users.pd_consent_at`) |
| NFR-32 | `audit_log` без `UPDATE`, `DELETE`, `TRUNCATE` для роли приложения |
| NFR-19, 21 | Toast при потере связи, вёрстка от 320×568 |
| REST §2.8 | Лимит 5 неудачных входов за 15 минут, ротация refresh-токенов |

## 3. Новые термины

- **Docker Compose** — файл, который описывает все сервисы проекта (БД, брокер, хранилище, API, фронтенд) и поднимает их одной командой, каждый в своём контейнере.
- **Миграция** — пронумерованный файл с изменением схемы БД. Alembic помнит, какие уже применены (служебная таблица `alembic_version`).
- **Сид (seed)** — начальные данные для разработки: жанры, лицензии, тестовые пользователи.
- **JWT (access-токен)** — подписанная сервером строка с ID пользователя, ролями и сроком жизни (1 час). Сервер проверяет подпись и не ходит в БД на каждый запрос.
- **Refresh-токен** — длинная случайная строка, которой клиент получает новую пару токенов, когда access истёк. В БД хранится только её хэш. **Ротация:** использованный refresh сразу аннулируется и выдаётся новый. Если кто-то предъявит уже использованный токен (признак кражи), отзывается вся цепочка токенов этого входа — «семейство».
- **Argon2id** — алгоритм хэширования паролей, который специально медленный и требует много памяти: перебирать пароли по украденной базе дорого.
- **Presigned POST** — разрешение от сервера браузеру загрузить один файл прямо в S3, с подписью, сроком жизни и ограничением размера. В срезе 0 так грузится аватар — маленькая репетиция загрузки битов.

## 4. Как пройдут запросы

### Регистрация (`POST /v1/auth/register`)

1. Браузер: форма проверяет email, пароль по NFR-5 и галочки согласий; без них кнопка неактивна.
2. Core API: Pydantic проверяет тело; при ошибках — `400 VALIDATION_ERROR` с `details` по полям.
3. Одна транзакция БД:
   - `INSERT users` (email в нижнем регистре — GAP-12, хэш пароля, `pd_consent_at = now()`);
   - `INSERT user_roles` (`artist`);
   - `INSERT profiles` (`display_name`);
   - `INSERT audit_log` (`user.registered`, `pep_agreement.accepted`);
   - `INSERT refresh_tokens` (хэш нового refresh-токена).
4. Ответ `201 Created` с парой токенов. Email уже занят → `409 EMAIL_TAKEN`.

### Вход и обновление токенов

- `POST /auth/login`: сначала подсчёт неудач в `login_attempts` за 15 минут; если их 5 и больше → `429 TOO_MANY_ATTEMPTS`, пароль даже не проверяется. Иначе проверка хэша → запись попытки → пара токенов или `401 INVALID_CREDENTIALS` с одним и тем же текстом для «нет такого email» и «неверный пароль».
- `POST /auth/refresh`: найти токен по хэшу → если он уже отозван, отозвать всё семейство и ответить `401` → иначе отозвать его и выдать новый в том же семействе.
- `POST /auth/logout`: отозвать переданный refresh-токен, ответ `204`.

### Аватар (`POST /users/me/avatar` → загрузка → `PUT /users/me`)

Браузер запрашивает форму загрузки → Core API выдаёт presigned POST в `temp-uploads` (ключ `avatars/{user_id}/{uuid}`, лимит 5 МБ, срок 1 час) → браузер грузит файл прямо в MinIO → `PUT /users/me` с `avatar_key` → Core API проверяет, что ключ принадлежит этому пользователю, скачивает файл, проверяет сигнатуру и размеры (NFR-22), копирует в `public-media` и пишет ключ в `profiles.avatar_key`.

### Подключение к продажам (`POST /users/me/producer-account`)

Проверки: роль Продюсера уже есть → `409 ALREADY_PRODUCER`; нет `billing_profiles` → `409 BILLING_REQUIRED`. Одна транзакция: `INSERT producer_accounts` (`tax_status`, `yookassa_account_id`, `pep_agreement_at = now()`), `INSERT user_roles` (`producer`), `INSERT audit_log` (`producer.connected` с фактом принятия соглашения о ПЭП и типовых условий лицензий). Ответ `201`. Новые роли попадут в access-токен при следующем обновлении, поэтому клиент сразу запрашивает новую пару.

Диаграммы последовательности для этих сценариев в документации нет. Используемые таблицы — на `assets/database_erd.png`: блок пользователей слева.

## 6. База данных

- **Роли PostgreSQL** (скрипт инициализации контейнера, GAP-5): `ohbeat_owner` — владелец схемы и миграций; `ohbeat_app` — `NOLOGIN`, права из шапки `schema.sql`; `ohbeat_api` — `LOGIN`, входит в `ohbeat_app`, под ним работает Core API.
- **Миграция `0001`:** копия `schema.sql` из документации без изменений + `GRANT`/`REVOKE` из её шапки.
- **Миграция `0002`** (ADR 0007): `refresh_tokens`, `login_attempts`, `UNIQUE` на `contracts.order_item_id`, индексы, права для `ohbeat_app`.
- **Сиды:** около 12 жанров; 4 лицензии с флагами из `User_Stories.md` §2.2; Артист, Продюсер (с данными покупателя и `yookassa_account_id`) и Администратор. Логины и пароли сидов — в `.env.example`.

Таблицы в работе: `users`, `user_roles`, `profiles`, `billing_profiles`, `producer_accounts`, `audit_log`, `genres`, `licenses`, `refresh_tokens`, `login_attempts`.

## 9. Экраны

Шапка (логотип, переключатель RU/EN, вход и регистрация или меню пользователя), регистрация, вход, профиль (имя, описание, аватар с миниатюрой), «Данные покупателя» по UI-спецификации §2 (переключатель физлицо / ИП или юрлицо, капитализация ФИО, маска телефона и замена «8» на «+7», ИНН с контрольной суммой, ссылка на Политику ПД), «Подключиться к продажам». Toast при потере связи.

Решение по хранению токенов в браузере: access-токен — в памяти страницы, refresh-токен — в `localStorage`. Контракт API передаёт refresh в теле запроса, поэтому cookie не подходит. Риск — кража токена через XSS; защищаемся тем, что React экранирует вывод, и ротацией токенов.

## 10. Тесты

- Миграция `0001` даёт тот же `pg_dump --schema-only`, что и прямое применение `schema.sql`.
- NFR-32: под `ohbeat_api` запросы `UPDATE`, `DELETE`, `TRUNCATE` к `audit_log` → `permission denied`.
- FR-31: регистрация без согласий → `400`; слабые пароли (по одному нарушению правила NFR-5) → `400`; занятый email (в любом регистре) → `409`; записи в `audit_log` и роль `artist`.
- Вход: 5 неудач → шестая попытка `429` даже с верным паролем; одинаковый ответ для неизвестного email и неверного пароля.
- Refresh: ротация; повторное предъявление старого токена отзывает семейство; logout.
- FR-32: валидация «Данных покупателя» (ИНН 10 и 12 цифр с контрольной суммой, обязательные поля организации, E.164); аватар неверного формата или размера отклоняется.
- FR-33: без данных покупателя → `409 BILLING_REQUIRED`; повторно → `409 ALREADY_PRODUCER`; роль `producer` и запись в `audit_log`.
- Фронтенд (Vitest): правила пароля, ИНН, маска телефона.

## 11. Как вы сможете проверить и посмотреть своими глазами

1. `docker compose up --build` — все сервисы healthy.
2. Swagger `http://localhost:8000/docs`: зарегистрироваться прямо оттуда и сравнить ответ с REST §2.8.
3. Интерфейс `http://localhost:5173`: регистрация, вход, профиль, данные покупателя, подключение к продажам.
4. SQL в psql:
   - `SELECT * FROM audit_log ORDER BY id DESC;` — записи о согласиях;
   - `SELECT token_hash, revoked_at FROM refresh_tokens;` — в БД только хэши, никаких токенов;
   - `SELECT password_hash FROM users LIMIT 1;` — строка Argon2, а не пароль.
5. MinIO Console: загруженный аватар лежит в `public-media`.
6. Логи: `docker compose logs api`.
