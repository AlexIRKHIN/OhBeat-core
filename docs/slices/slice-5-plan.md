## 1. Что получится

Администратор входит своей учётной записью (`SEED_ADMIN_*`) и видит раздел «Администрирование» с четырьмя вкладками:

1. **Журнал** — Audit Log с фильтрами по действию, сущности и периоду. Только чтение: ни интерфейс, ни API не умеют менять записи, а роль приложения в БД не имеет на это прав (NFR-32, уже проверено тестом среза 0).
2. **Жанры** — список с числом битов в каждом жанре, добавление и удаление. Жанр, который используется хоть в одном бите, удалить нельзя.
3. **Стоп-лист** — добавление и удаление запрещённых слов. Новое слово сразу работает при публикации битов.
4. **Зависшие биты** — биты, которые остались в `processing` после исчерпания повторов. Для каждого две кнопки: «Повторить обработку» и «Отклонить» с причиной. Продюсер получает письмо, оба действия попадают в Audit Log.

## 2. Требования

| Требование | Что делаем |
| --- | --- |
| FR-35, NFR-32 | `GET /admin/audit-log` с фильтрами и постраничной выдачей; записей не меняем и не удаляем |
| FR-36 | Жанры: список, добавление, удаление; используемый жанр → `409 GENRE_IN_USE`. Стоп-лист: список, добавление, удаление |
| FR-37 | Список застрявших битов; «Повторить» — новое событие в `outbox`; «Отклонить» — `rejected` с причиной; письмо Продюсеру; Audit Log |
| REST §2.13 | Всё только для роли `admin`, иначе `403 FORBIDDEN` |
| NFR-7 | В Audit Log пишутся и действия Администратора со справочниками (это не требуется явно, но журнал без них неполон) |

## 3. Новые термины

- **DLQ (dead letter queue, «очередь мёртвых писем»).** Сюда RabbitMQ складывает сообщение, если его не удалось обработать после всех повторов (у нас 30 с, 2 мин, 10 мин). Оно там лежит и ждёт человека.
- **«Застрявший» бит.** Его сообщение ушло в DLQ, а бит так и остался в `processing`. Core API не видит DLQ напрямую, поэтому отличает такой бит по времени: в обработке дольше 30 минут (GAP-21). Это сумма всех повторов, около 13 минут, плюс запас.
- **Фасеты фильтра.** Список значений для выпадающих меню фильтра. Например, все действия, которые встречаются в журнале: `payment.succeeded`, `contract.signed` и т. д.

## 4. Как пройдёт повтор обработки

```
бит в processing → Worker трижды не смог (например, антивирус недоступен) → сообщение в beat_processing_dlq
                 → прошло 30 минут с отправки задачи → бит в списке «Зависшие»
Администратор «Повторить» → POST /admin/beats/{id}/reprocess
     одна транзакция: проверить, что бит всё ещё processing
                      → INSERT outbox (та же задача: те же файлы из temp-uploads, те же параметры)
                      → audit_log admin.beat_reprocessed
     → relay публикует задачу → Worker обрабатывает → active или rejected → письмо Продюсеру (как в срезе 1)
Администратор «Отклонить» → POST /admin/beats/{id}/reject {reason}
     одна транзакция: processing → rejected, rejection_reason, audit_log admin.beat_rejected
     → после коммита письмо Продюсеру
```

Если исходники уже удалены правилом хранения `temp-uploads` (24 часа), Worker сам отклонит бит с понятной причиной (GAP-22, сделано в срезе 1). Если запоздалый результат старой задачи всё-таки придёт после решения Администратора, он будет проигнорирован: обработчик результатов принимает их только для битов в `processing` (срез 1).

## 5. Эндпоинты Core API

| Метод и путь | Главные ответы |
| --- | --- |
| `GET /v1/admin/audit-log?action=&entity=&entity_id=&from=&to=&cursor=&limit=` | `200 {items: [{id, occurred_at, action, entity, entity_id, actor: {id, email}, ip, details}], next_cursor}` |
| `GET /v1/admin/audit-log/facets` | `200 {actions: [...], entities: [...]}` — значения для фильтров (GAP-75) |
| `GET /v1/admin/genres` | `200 [{id, name, beats_count}]` |
| `POST /v1/admin/genres` `{name}` | `201`; `400 VALIDATION_ERROR`; `409 DUPLICATE` |
| `DELETE /v1/admin/genres/{id}` | `204`; `409 GENRE_IN_USE`; `404` |
| `GET /v1/admin/stop-words` | `200 [{id, word, created_at}]` |
| `POST /v1/admin/stop-words` `{word}` | `201`; `400`; `409 DUPLICATE` |
| `DELETE /v1/admin/stop-words/{id}` | `204`; `404` |
| `GET /v1/admin/beats?status=processing` | `200 [{id, title, producer, processing_since, stuck}]`. По умолчанию только застрявшие; `&all=true` — все в обработке |
| `POST /v1/admin/beats/{id}/reprocess` | `202`; `409 INVALID_STATUS` |
| `POST /v1/admin/beats/{id}/reject` `{reason}` | `200`; `400` (причина 3–500 символов); `409 INVALID_STATUS` |

Все — только `admin`: без входа `401`, с другой ролью `403`. Новых таблиц и миграций нет.

## 6. Решения, которые я предлагаю (новые GAP)

- **GAP-74. С какого момента бит «в обработке».** Колонки нет, а подтверждение загрузки в Audit Log не пишется. Беру время последнего события `beat.media.process` этого бита из `outbox`: строки там не удаляются после отправки. «Повторить» добавляет новое событие, и отсчёт начинается заново. Порог «застрял» — 30 минут (GAP-21), настройка `STUCK_PROCESSING_MINUTES`.
- **GAP-75. Фильтры журнала.**
  - `action` — точное имя или префикс с точкой на конце: `payment.` покажет все платёжные события;
  - `entity` и `entity_id` — точно;
  - `from` и `to` — даты по Москве, оба конца включены, как в статистике продаж (GAP-69);
  - выдача — новые сначала, курсором по `(occurred_at, id)`, по 50 записей (не больше 200);
  - для выпадающих меню — `GET /admin/audit-log/facets`;
  - Администратор видит email автора действия: это его рабочая задача, а данные уже есть в БД.
- **GAP-76. Правила справочников.**
  - Жанр — 2–64 символа, уникален без учёта регистра.
  - «Используется» — есть хоть одна строка в `beat_genres`, включая удалённые логически биты: на них ссылаются купленные лицензии, и внешний ключ всё равно не даст удалить такой жанр.
  - Переименования нет: в REST его нет.
  - Стоп-слово — одно слово, 2–100 символов. Хранится в нижнем регистре с «ё» → «е», как при проверке (GAP-16). Дубликат → `409 DUPLICATE`.
  - Новое слово действует только для новых битов. Уже опубликованные не перепроверяются: это решение для модерации, а в FR его нет.
- **GAP-77. DLQ после решения Администратора.** Старое сообщение остаётся в `beat_processing_dlq`, Core API его не трогает. Его видно и можно удалить в веб-интерфейсе RabbitMQ. Автоматической очистки DLQ в документации нет, и это не мешает: повтор идёт новым событием.

## 7. Экраны

- В шапке у Администратора пункт «Администрирование»; маршрут `/admin` доступен только роли `admin`.
- **Журнал:**
  - фильтры: действие, сущность, ID, период;
  - таблица: время по Москве, действие, сущность и ID, автор, IP, кнопка «Подробности» — раскрывает `details` как JSON;
  - «Показать ещё»; пустое состояние; на телефоне — карточки вместо таблицы.
- **Жанры:** поле «Новый жанр», список с числом битов. Кнопка удаления у используемых жанров выключена с подсказкой «Используется в N битах». Удаление — после подтверждения в окне.
- **Стоп-лист:** поле добавления и список с кнопками удаления (с подтверждением). Подсказка: «Слова проверяются без учёта регистра, ё = е, по целым словам».
- **Зависшие биты:** название, Продюсер, «в обработке с …», «Повторить», «Отклонить» (окно с полем причины). Переключатель «Показать все в обработке».

## 8. Тесты

| Тест | Как |
| --- | --- |
| Доступ | каждый эндпоинт: гость → `401`, Артист и Продюсер → `403`, Администратор → `200` |
| FR-35 фильтры | действие (точно и префиксом), сущность, ID, период по Москве, курсор без пропусков и повторов |
| NFR-32 | у `/admin/audit-log` нет `PUT`/`PATCH`/`DELETE` (`405`); права роли в БД — уже есть в `test_schema.py` |
| FR-36 жанры | добавить → появился в `/dictionaries` и в форме загрузки; дубликат без учёта регистра → `409`; удалить неиспользуемый → `204`; используемый (в том числе только удалённым битом) → `409 GENRE_IN_USE` |
| FR-36 стоп-лист | добавить «Ёжик» → `POST /beats` с «ежик» в названии → `400 Запрещенное слово`; удалить → проходит |
| FR-37 список | бит в `processing` 31 минуту → в списке; 5 минут → нет (есть с `all=true`) |
| FR-37 повтор | `reprocess` → новое событие в `outbox` с теми же файлами, отсчёт сброшен, Audit Log; не `processing` → `409` |
| FR-37 отклонение | `reject` → `rejected` с причиной, письмо Продюсеру, Audit Log; запоздалый результат Worker'а после этого игнорируется |
| Сквозной FR-37 с настоящим Worker'ом | мок антивируса `unavailable` + короткие задержки повторов → сообщение в DLQ → `reprocess` при исправном антивирусе → бит `active` |

## 9. Как вы сможете проверить и посмотреть своими глазами

1. Войдите Администратором (`SEED_ADMIN_*` в `.env`) → «Администрирование» → «Журнал». Отфильтруйте `payment.` и найдите оплату заказа № 5, потом `contract.signed`.
2. «Жанры»: попробуйте удалить Trap (используется) — кнопка выключена, а API ответит `409 GENRE_IN_USE`. Добавьте «Phonk» и удалите его.
3. «Стоп-лист»: добавьте слово. Войдите Продюсером и попробуйте опубликовать бит с этим словом в названии.
4. Зависший бит, если не ждать 30 минут:
   - в `.env`: `ANTIVIRUS_MODE=unavailable`, `STUCK_PROCESSING_MINUTES=1` и короткие задержки повторов (точные строки будут в отчёте), затем `docker compose up -d`;
   - загрузите бит со стемами. В RabbitMQ (<http://localhost:15672>) видно, как сообщение проходит очереди задержки и оказывается в `beat_processing_dlq`;
   - верните `ANTIVIRUS_MODE=normal`, перезапустите Worker → «Зависшие биты» → «Повторить» → бит опубликован.
5. Снова «Журнал»: `admin.beat_reprocessed`, `admin.genre_created`, `admin.stop_word_added`.
