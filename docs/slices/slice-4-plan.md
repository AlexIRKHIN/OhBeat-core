# Срез 4. Подпись Exclusive кодом из SMS — план

Статус: **ждёт «ок» аналитика**. Общий план — [PLAN.md](../PLAN.md). Источники:
- [RFC ПЭП](../../../OhBeat-System-Analysis/02_Architecture/RFC_Digital_Signature.md) §2–§6;
- `assets/src/sequence_exclusive_purchase.puml`, раздел «Подписание договора»;
- NFR-7, NFR-31, FR-26;
- REST API §2.12 (`contract-draft`).

## 1. Что получится

Артист оформляет заказ с Exclusive. На странице заказа появляется блок «Договор на Exclusive»: полный текст проекта и его SHA-256. Артист нажимает «Подписать», и на телефон из данных покупателя уходит 6-значный код (мок SMS пишет его в лог). Артист вводит код, договор подписан, кнопка «Перейти к оплате» становится активной. После оплаты PDF получает штамп ПЭП по RFC §5. Это последний недостающий кусок: после среза Exclusive покупается целиком, от корзины до скачивания стемов.

Всё время подписи идёт резерв на 15 минут: обратный отсчёт виден рядом. Подпись резерв не продлевает (FR-18).

## 2. Требования

| Требование | Что делаем |
| --- | --- |
| RFC §2, FR-17 | Без подписи `POST /orders/{id}/payments` → `428` (уже есть). Подпись — до создания платежа |
| RFC §3, п. 2 | Текст проекта Артист видит до запроса кода: `GET /orders/{id}/contract-draft` |
| RFC §3, п. 3; §6 | Проверка кода → строка `contracts` (`otp`, `draft_sha256`, `signer_phone`, `signer_ip`, `signed_at`) на **каждую** позицию Exclusive (GAP-28) + Audit Log |
| RFC §4 | `POST …/signature/otp` → `202 {expires_at, resend_after}`; `POST …/signature/verify` → `200 {signed_at}` и ошибки `INVALID_CODE`, `CODE_EXPIRED`, `CODE_ATTEMPTS_EXCEEDED`, `TOO_MANY_REQUESTS`, `PHONE_REQUIRED` |
| NFR-31 | 6 цифр; живёт 5 минут; 3 попытки на код; повтор не раньше 60 с; не больше 5 отправок в час **на пользователя**; в БД только хэш |
| FR-26, RFC §5 | Штамп ПЭП в PDF: телефон под маской, «одноразовый SMS-код», время по Москве, основание (соглашение о ПЭП Продюсера), полный SHA-256 проекта, номер договора. Штамп уже написан в 3c, здесь он впервые работает на живых данных |
| NFR-7 | Audit Log: отправка кода (с хэшами проектов, GAP-9), неверная попытка, подпись каждого договора |

## 3. Новые термины

- **OTP (one-time password)** — одноразовый код. Им Артист подтверждает: «этот текст подписываю я, владелец этого телефона».
- **HMAC** — хэш с секретным ключом. Обычный SHA-256 от 6 цифр бесполезен: все миллион вариантов перебираются за доли секунды, и по утёкшей базе код восстановят. С HMAC без секрета, который лежит в `.env`, а не в БД, перебор невозможен. Поэтому в `signature_otps.code_hash` будет HMAC, как и записано в PLAN.md.
- **Ограничение частоты (rate limit)** — не чаще одного кода в 60 с и не больше 5 в час. Защищает кошелёк платформы (SMS платные) и телефон покупателя от «бомбардировки».
- **Блокировка строки при проверке кода.** Если отправить 10 неверных кодов одновременно, без блокировки все 10 прочитают «попыток использовано 0» и пройдут проверку. Поэтому строку кода читаем через `SELECT … FOR UPDATE`: запросы встают в очередь, и счётчик честно доходит до 3.

## 4. Как пройдёт подпись

По диаграмме `sequence_exclusive_purchase`, раздел «Подписание договора (ПЭП)»:

```
Артист ─GET /orders/{id}/contract-draft─► Core API: собрать текст по каждой позиции Exclusive
                                          из снимка заказа → текст + draft_sha256 (ничего не пишет)
       ─«Подписать»─► POST /orders/{id}/signature/otp
            заказ pending, резерв жив, ещё не подписан? лимиты 60 с / 5 в час?
            одна транзакция:
              старые коды заказа → expires_at = now()   (новый код отменяет старый, GAP-34)
              INSERT signature_otps (HMAC кода, expires_at = +5 мин, created_at)
              audit_log signature.otp_sent {draft_sha256 по позициям}   (GAP-9)
              SMS через интерфейс Notifier → мок пишет «SMS to=+7… code 583204» в лог
            COMMIT → 202 {expires_at, resend_after}
       ─вводит код─► POST /orders/{id}/signature/verify {code}
            одна транзакция:
              SELECT действующий код … FOR UPDATE
              истёк → 410 CODE_EXPIRED; 3 попытки уже были → 429 CODE_ATTEMPTS_EXCEEDED
              HMAC не совпал → attempts + 1, audit → 400 INVALID_CODE {attempts_left}
              совпал → confirmed_at; пересчитать draft_sha256; INSERT contracts (otp) на каждую позицию;
                       audit contract.signed
            COMMIT → 200 {signed_at}
       ─«Перейти к оплате»─► дальше как в срезе 3: холд → FR-23 → capture → PDF со штампом ПЭП
```

Почему хэш проекта пересчитывается при проверке, а не берётся из момента отправки: хранить его между шагами негде (GAP-9). Текст строится только из неизменяемых данных заказа, поэтому получается тот же самый. На всякий случай хэш на момент отправки пишется в Audit Log, и их можно сверить.

## 5. Эндпоинты Core API

| Метод и путь | Доступ | Главные ответы |
| --- | --- | --- |
| `GET /v1/orders/{id}/contract-draft` | владелец | `200 {items: [{item_id, contract_number, title, license, text, draft_sha256}]}`; `403`; `409 INVALID_STATUS` (заказ не `pending`) |
| `POST /v1/orders/{id}/signature/otp` | владелец | `202 {expires_at, resend_after}`; `409 INVALID_STATUS` (не `pending` или резерв истёк); `409 ALREADY_SIGNED`; `409 PHONE_REQUIRED`; `429 TOO_MANY_REQUESTS` с `retry_after`; `503 SMS_UNAVAILABLE` |
| `POST /v1/orders/{id}/signature/verify` | владелец | `200 {signed_at}`; `400 INVALID_CODE {attempts_left}`; `410 CODE_EXPIRED`; `429 CODE_ATTEMPTS_EXCEEDED`; `409 INVALID_STATUS` / `ALREADY_SIGNED` |

Без новых эндпоинтов: `GET /orders/{id}` уже отдаёт `requires_signature` и `signed`, а `POST /orders/{id}/payments` уже отвечает `428`.

## 6. Изменения в БД — нужно ваше решение

В `signature_otps` нет времени отправки кода. Без него не проверить «повтор не раньше 60 с» и «5 отправок в час» (GAP-70). Есть два варианта:

| | Плюсы | Минусы |
| --- | --- | --- |
| **А. Миграция `0003`: колонка `created_at TIMESTAMPTZ NOT NULL DEFAULT now()` и индекс** | Время честное и хранится явно. Тот же подход, что в ADR 0007 (дополнения к `schema.sql` — отдельной миграцией). Эталонная `0001` не меняется | Ещё одно отличие от `schema.sql`. Оно записывается в GAP и в комментарий миграции |
| Б. Без миграции: время отправки = `expires_at − 5 минут` | Схема ровно как в документации | Хрупко. Если для демонстрации поменять срок жизни кода в настройках, лимиты начнут считаться неверно, а старые коды станут «старше» или «моложе» |

**Рекомендую А.** Вместе с колонкой — индекс `(order_id, created_at)`. Лимит «на пользователя» считается через `orders.customer_id`, отдельная колонка пользователя не нужна.

## 7. Мок SMS

- В интерфейс `Notifier` добавляется `send_sms(phone, text)`. Мок пишет строку `SMS to=+7900*****67 | OhBeat: код 583204 …` в лог `api`. Код в логе — это и есть «доставка» в локальной среде (CLAUDE.md).
- `SMS_MODE=unavailable` в `.env` — мок изображает недоступность, как мок антивируса. Тогда код не сохраняется, лимит не тратится, ответ `503 SMS_UNAVAILABLE` (GAP-72).

## 8. Экраны

- **Страница заказа**, пока заказ `pending` с Exclusive и без подписи — блок «Договор на Exclusive»:
  - текст проекта в прокручиваемой рамке, номер договора и SHA-256 (по каждой позиции Exclusive);
  - «Подписать» → поле кода: 6 цифр, `inputmode="numeric"`, `autocomplete="one-time-code"` — телефоны сами подставляют код из SMS;
  - «Код отправлен на +7 (900) ***-**-67», отсчёт срока жизни кода, «Отправить код ещё раз» активна через 60 с;
  - ошибки по-человечески: «Неверный код, осталось попыток: 2», «Код истёк — запросите новый», «Попытки закончились — запросите новый код», «Слишком часто — повторите через 0:45»;
  - после подписи: «Договор подписан 12.11.2026 14:22 (МСК)», и «Перейти к оплате» становится активной.
- **Оформление:** без изменений, после создания заказа с Exclusive сразу переходим на страницу заказа (уже так).
- **Резерв истёк во время подписи:** блок подписи прячется, остаётся «Время резерва вышло» и ссылка в корзину.

Экрана подписи в `UI_Specifications.md` нет — тексты и поведение выше предлагаю я (GAP-71).

## 9. Обязательные тесты

| Тест | Как |
| --- | --- |
| **3 неверные попытки** | 1-я и 2-я → `400 {attempts_left: 2 / 1}`, 3-я → `400 {attempts_left: 0}`, 4-я и даже верный код → `429 CODE_ATTEMPTS_EXCEEDED` |
| **Одновременный перебор** | 10 параллельных `verify` с неверными кодами → ровно 3 попытки засчитаны, остальные `429`; верный код после этого не проходит |
| **Срок жизни 5 минут** | подменяем «текущее время» в БД → `410 CODE_EXPIRED` |
| **Повтор не раньше 60 с** | второй запрос через 10 с → `429` с `retry_after ≈ 50`; через 61 с → `202` |
| **5 в час на пользователя** | пять отправок по двум разным заказам одного Артиста → шестая `429`; другой Артист не затронут |
| **Новый код отменяет старый** | запрос, ещё запрос (через 60 с) → старый код больше не принимается |
| **Только хэш** | в `signature_otps.code_hash` нет кода в открытом виде, HMAC с другим секретом не совпадает |
| **Одноразовость** | после успешной подписи тот же код → `409 ALREADY_SIGNED` |
| **Подпись и PDF** | заказ с двумя Exclusive и одним Basic: два договора `otp` + один `offer_accept`; после оплаты в PDF штамп ПЭП, `draft_sha256` в штампе = `contracts.draft_sha256`, `pdf_sha256` = хэш файла |
| **Сквозной Exclusive** | подпись → платёж → холд → `sold` → PDF → ссылки на MP3, WAV, стемы и договор |

Ещё: резерв истёк → `409 INVALID_STATUS` на `otp` и `verify`; чужой заказ → `403`; заказ без Exclusive → `409 INVALID_STATUS`; `SMS_UNAVAILABLE` не тратит лимит; телефон в штампе под маской; Audit Log содержит отправку, неверные попытки и подпись.

## 10. Как вы сможете проверить и посмотреть своими глазами

1. Войдите Артистом, положите в корзину Exclusive (например, Gold Chains или Nova Pulse у Nova Sound) и оформите заказ.
2. На странице заказа прочитайте договор и нажмите «Подписать». Код возьмите из лога:
   ```bash
   docker compose logs api | grep SMS
   ```
3. Дважды введите неверный код и посмотрите на счётчик попыток. Потом введите верный.
4. «Перейти к оплате» → «Успешная оплата» → скачайте договор и посмотрите штамп ПЭП.
5. В БД:
   - `SELECT id, attempts, expires_at, confirmed_at, code_hash FROM signature_otps;` — кода в открытом виде нет;
   - `SELECT signature_type, signer_phone, draft_sha256 FROM contracts;`
   - `SELECT action, details FROM audit_log WHERE action LIKE 'signature%' OR action = 'contract.signed';`
6. `SMS_MODE=unavailable` в `.env` → `docker compose up -d` → «Подписать» → «SMS-сервис временно недоступен».

## 12. Оценка и порядок

Сложность **M**, одна часть без деления:

1. миграция `0003` (если выберете вариант А) и мок SMS;
2. эндпоинты и тесты, включая одновременный перебор;
3. блок подписи на странице заказа;
4. сквозная проверка Exclusive в браузере, отчёт.
