# Срез 3. Покупка: корзина → заказ → резерв → платёж → вебхук → выдача — план

Статус: **ждёт «ок» аналитика**. Общий план — [PLAN.md](../PLAN.md). Диаграммы: `assets/sequence_exclusive_purchase.png`, `assets/src/order_lifecycle.puml`, `assets/src/beat_lifecycle.puml`. Требования: FR-14…FR-30, FR-34 (статистика продаж, перенесена из среза 1).

## 1. Что получится

Артист выбирает лицензию на странице бита и кладёт её в корзину. В корзине видны цены Продюсеров, отдельной строкой комиссия сервиса и итог. При оформлении Артист отмечает согласие с офертой, переходит на страницу оплаты мока ЮKassa и выбирает тестовую карту. Деньги холдируются, Core API по вебхуку проверяет, можно ли продать, подтверждает списание, генерирует PDF-договоры и открывает файлы. После этого «Мои покупки» выдают ссылки на скачивание, которые живут час. Продюсер видит продажу в статистике, а мок показывает, сколько денег ушло каждому Продюсеру.

**Про Exclusive.** Вся логика Exclusive делается и проверяется тестами в этом срезе: резерв на 15 минут, гонка покупателей, продажа и отмена при холде, истёкший резерв. Но оплатить Exclusive через интерфейс можно будет только после среза 4. По RFC платёж без подписи по SMS запрещён (`428 SIGNATURE_REQUIRED`), а подпись появится в срезе 4. В тестах подпись подставляется заготовленной строкой `contracts`.

## 2. Требования

| Требование | Что делаем |
| --- | --- |
| FR-14 | Корзина: одна лицензия на бит, смена лицензии заменяет прежнюю; бит не `active` или лицензия выключена → нельзя |
| FR-15 | В корзине цены Продюсеров, строка «Комиссия сервиса» и итог; при оформлении сверяются цены, которые видел Артист (`expected_price`) → `409 PRICE_CHANGED` и подтверждение новой суммы |
| FR-16, FR-17 | Галочка оферты для Basic/Premium/Trackout; «Перейти к оплате» неактивна без неё. Для Exclusive — `428` до подписи (срез 4) |
| FR-18 | Одна транзакция: заказ `pending`, позиции с ценой и комиссией, снимок данных покупателя; резерв Exclusive атомарным `UPDATE … WHERE status = 'active'` |
| FR-19 | Бит в резерве: в корзину и в новые заказы нельзя ни с какой лицензией |
| FR-20, FR-21 | Платёж в ЮKassa: `capture: false`, redirect, `return_url`, `metadata.order_id`, `transfers` по Продюсерам, `Idempotence-Key`; до 3 повторов при недоступности → `503` |
| FR-22 | Вебхук: проверка IP (выключена настройкой), сверка `GET /v3/payments/{id}`, дедупликация в `payment_events`, `200` после коммита |
| FR-23 | Холд → проверка продажи → `capture` или `cancel` (заказ `canceled`, письмо с причиной); окончательный сбой `capture` → бит снова `active` |
| FR-24 | `succeeded` → заказ `paid` (в том числе из `expired`), резерв снят, Exclusive скрыт, письмо Продюсеру, Audit Log |
| FR-25 | `canceled` (отказ банка) → платёж `canceled`, заказ остаётся `pending` до истечения, можно оплатить снова новым ключом |
| FR-26 | PDF договора на каждую оплаченную позицию: стороны, условия, отметка о подписании; файл в `private-media`, `pdf_sha256` в БД |
| FR-27 | Страница возврата опрашивает заказ каждые 2 с до 60 с; затем — «Оплата обрабатывается…»; письмо со ссылкой на «Мои покупки» |
| FR-28 | `GET /orders/{id}/downloads`: presigned GET на 1 час, только владельцу оплаченного заказа |
| FR-29 | Планировщик раз в минуту: оба запроса из `Database_Schema.md` §6 |
| FR-30, NFR-25 | Комиссия сверх цены из настроек, фиксируется в `order_items.platform_fee`; `transfers` по каждому Продюсеру на его `yookassa_account_id` |
| FR-34 | «Мои продажи»: проданные позиции и сумма за период |
| NFR-7 | Audit Log: заказ, акцепт оферты, каждое платёжное событие, `capture`/`cancel`, генерация договора |
| NFR-8 | Ссылки на файлы генерируются при каждом запросе и нигде не хранятся |
| NFR-27, NFR-29 | Рубли с копейками, время в договоре по Москве |

## 3. Новые термины

- **Двухстадийный платёж (холд)** — деньги сначала только блокируются на карте (`waiting_for_capture`), а списываются (`capture`) отдельной командой. Если продать нельзя, холд снимается (`cancel`), и Артист ничего не теряет.
- **Вебхук** — запрос, который ЮKassa сама присылает нам, когда меняется статус платежа. Ему нельзя верить на слово: любой может прислать такой запрос. Поэтому статус всегда перепроверяется у ЮKassa (`GET /v3/payments/{id}`).
- **Idempotence-Key** — метка запроса к ЮKassa. Если мы повторим запрос с той же меткой (например, после таймаута), ЮKassa вернёт тот же платёж, а не создаст второй.
- **Дедупликация вебхука** — ЮKassa может прислать одно уведомление несколько раз. В `payment_events` пара «платёж + событие» уникальна: второй раз строка не вставится, и обработка не повторится.
- **Сплитование** — деньги одного платежа сразу делятся: каждому Продюсеру — его цена, платформе — комиссия.
- **Presigned GET** — подписанная ссылка на скачивание одного файла из приватного бакета, живёт час.
- **Мок ЮKassa** — наша маленькая программа, которая ведёт себя как ЮKassa: те же адреса, ответы и вебхуки, плюс пульт для поломок.

## 4. Как пройдёт покупка

По `sequence_exclusive_purchase.png`, для Basic без подписи:

```
Артист ─PUT /cart/items/{beat}─► Core API ─► cart_items
       ─GET /cart──────────────► цены, комиссия, итог
       ─POST /orders───────────► одна транзакция:
                                  orders(pending, снимок данных покупателя и Продюсеров)
                                  order_items(цена, комиссия)
                                  [Exclusive] UPDATE beats SET reserved … WHERE status='active'
                                  contracts(offer_accept) + audit_log
       ─POST /orders/{id}/payments─► Core API ─POST /v3/payments (Idempotence-Key, transfers)─► мок ЮKassa
       ◄─confirmation_url─────────────────────────────────────────────────────────────────────┘
       ─► страница оплаты мока → «Успешная оплата» ─► холд
                                     мок ─вебхук waiting_for_capture─► Core API
                                     Core API ─GET /v3/payments/{id}─► мок (сверка)
                                     одна транзакция: payment_events + проверки FR-23
                                       (Exclusive: UPDATE beats SET sold … WHERE active OR reserved этим заказом)
                                     после коммита: POST /v3/payments/{id}/capture ─► мок
                                     мок ─вебхук succeeded─► Core API: заказ paid, PDF договоров, audit_log, письма
       ◄─ redirect на страницу возврата ─ опрос GET /orders/{id} каждые 2 с ─ paid ─► ссылки на файлы
```

**Ветка отказа (FR-23).** Если бит уже продан или занят другим заказом, Core API в той же транзакции переводит заказ в `canceled` и снимает его резервы. После коммита он вызывает `cancel`, холд снимается, Артист получает письмо с причиной.

**Защита от потери `capture` (GAP-35).** Если Core API упадёт между коммитом и вызовом `capture`, задача планировщика раз в минуту найдёт платёж, который висит в холде, и доведёт его. Решение берётся из БД: заказ `canceled` → `cancel`, иначе → `capture`. Ключи идемпотентности у этих вызовов постоянные, поэтому повтор безопасен.

## 5. Деньги на примере

Корзина: бит Продюсера А за 1 500 ₽ (Basic) и бит Продюсера Б за 3 000 ₽ (Premium), комиссия 10% (`PLATFORM_FEE_PERCENT`).

| | Цена | Комиссия | К оплате |
| --- | --- | --- | --- |
| Бит А, Basic | 1 500,00 | 150,00 | |
| Бит Б, Premium | 3 000,00 | 300,00 | |
| **Итого** | 4 500,00 | 450,00 | **4 950,00 ₽** |

В ЮKassa уходит `amount = 4950.00` и `transfers`: Продюсеру А — 1 500,00, Продюсеру Б — 3 000,00. 450,00 остаются платформе. Комиссия считается по каждой позиции и округляется до копейки (GAP-42). Мок проверяет, что Σ transfers + комиссия = сумма платежа, иначе отвечает `400`. Комиссию он получает в `metadata.platform_fee` (GAP-41).

## 6. Эндпоинты Core API

| Метод и путь | Доступ | Главные ответы |
| --- | --- | --- |
| `GET /v1/cart` | вошедший | позиции с `available`, `items_total`, `service_fee`, `total` |
| `PUT /v1/cart/items/{beat_id}` | вошедший | `409 BEAT_RESERVED / BEAT_SOLD / BEAT_NOT_AVAILABLE / LICENSE_INACTIVE / OWN_BEAT` |
| `DELETE /v1/cart/items/{beat_id}` | вошедший | `204` |
| `POST /v1/orders` | вошедший | `201`; `409 BEAT_RESERVED / BEAT_SOLD / LICENSE_INACTIVE / PRICE_CHANGED / BILLING_REQUIRED / BEAT_NOT_AVAILABLE / OWN_BEAT` |
| `GET /v1/orders/{id}` | владелец | статус, суммы, позиции, срок резерва, последний платёж |
| `POST /v1/orders/{id}/payments` | владелец | `200 {payment_id, confirmation_url}`; `410 RESERVATION_EXPIRED`; `428 SIGNATURE_REQUIRED`; `409 INVALID_STATUS`; `503 PAYMENT_PROVIDER_UNAVAILABLE` |
| `POST /v1/payments/webhook` | ЮKassa (без токена) | `200` после коммита; `500` при сбое — ЮKassa повторит |
| `GET /v1/orders/{id}/downloads` | владелец | ссылки на 1 час; `403`; `409 ORDER_NOT_PAID` |
| `GET /v1/users/me/purchases` | вошедший | оплаченные позиции, `pdf_sha256` |
| `GET /v1/users/me/sales?from=&to=` | Продюсер | проданные позиции и сумма за период |

Таблицы: `cart_items`, `orders`, `order_items`, `payments`, `payment_events`, `contracts`, `beats`, `audit_log`. Новых таблиц и миграций нет.

## 7. Мок ЮKassa (новый контейнер `yookassa-mock`)

| Что | Как |
| --- | --- |
| API как у ЮKassa v3 | `POST /v3/payments`, `GET /v3/payments/{id}`, `POST /v3/payments/{id}/capture`, `POST /v3/payments/{id}/cancel`; авторизация shopId и секретным ключом из `.env` |
| Идемпотентность | тот же `Idempotence-Key` → тот же платёж |
| Проверка сплитования | Σ `transfers` + `metadata.platform_fee` = `amount`, иначе `400` |
| Страница оплаты | `confirmation_url` ведёт на страницу мока (`http://localhost:8100/checkout/…`) с кнопками: «Успешная оплата» (холд), «Отказ банка» (`canceled`, причина `insufficient_funds`), «Холд без уведомления» (вебхук не уходит). Потом редирект на `return_url` |
| Вебхуки | `waiting_for_capture`, `succeeded`, `canceled` на `http://api:8000/v1/payments/webhook`; если ответ не `200` — повторы с паузами 1, 2, 4, 8, 16 с, как делает настоящая ЮKassa |
| Пульт `http://localhost:8100/admin` | список платежей; «отправить вебхук ещё N раз»; поломка следующего запроса (таймаут, `500`, `429`) для create / capture / cancel; задержка вебхуков; перечисления Продюсерам после `succeeded` (FR-30) |
| Хранение | SQLite в томе `yookassa-data`: платежи переживают перезапуск |

Core API ходит в ЮKassa через интерфейс `PaymentGateway`: настоящий HTTP-клиент для мока и поддельный шлюз для тестов.

## 8. Договор (FR-26)

- Шаблон HTML (Jinja2) → PDF через WeasyPrint (ADR 0004). В образ Core API добавятся системные библиотеки и шрифт DejaVu с кириллицей.
- В договоре: номер `{order_id}-{n}` (GAP-32), стороны из снимка заказа — Лицензиар из `licensors`, Лицензиат из `buyer` (GAP-8), бит, лицензия, состав файлов, цена, условия (заглушка, GAP-31), дата по Москве.
- В конце — отметка о подписании. Для оферты: «Договор заключён акцептом оферты из учётной записи …, IP …, время …». Для Exclusive — штамп ПЭП из RFC §5 (срез 4).
- `draft_sha256` — хэш текста договора без отметки о подписании. Он считается при создании заказа (оферта) и при отправке кода (Exclusive). `pdf_sha256` — хэш готового PDF.

## 9. Экраны

- **Страница бита:** выбор лицензии и «В корзину». Кнопка неактивна, если бит в резерве, продан или ваш собственный. Гостя отправляет на вход.
- **Корзина** (значок с числом в шапке): позиции, цены, недоступные помечены и мешают оформлению, строка «Комиссия сервиса», итог, «Оформить заказ».
- **Оформление:**
  - если нет данных покупателя — ссылка на форму с возвратом сюда;
  - состав заказа и суммы, галочка оферты;
  - «Перейти к оплате» → заказ → платёж → переход на страницу оплаты;
  - при `PRICE_CHANGED` — окно с новыми ценами и «Подтвердить»;
  - при `BEAT_RESERVED` / `BEAT_SOLD` — тексты из FR-18;
  - при `503` — текст из FR-21.
- **Возврат после оплаты:**
  - опрос каждые 2 с до 60 с;
  - `paid` → ссылки на файлы и договоры;
  - отказ банка → «Оплата не прошла» и «Оплатить снова»;
  - `canceled` → причина;
  - таймаут → текст FR-27.
- **«Мои покупки»:** оплаченные позиции; «Скачать» каждый раз берёт свежие ссылки (NFR-8); `pdf_sha256` для сверки.
- **«Мои продажи»** для Продюсера: период, список и сумма.

## 10. Обязательные тесты

| Тест | Как |
| --- | --- |
| **Гонка двух покупателей за Exclusive** | 2 и 10 параллельных `POST /orders` на настоящем PostgreSQL → ровно один `201`, остальные `409 BEAT_RESERVED` |
| **Повторный вебхук** | то же событие 3 раза подряд и 3 раза одновременно → одна обработка, один `capture`, один PDF, каждый ответ `200` |
| **Истёкший резерв при `waiting_for_capture`** | бит снова свободен → `capture`, `sold`; бит занят другим заказом → `cancel`, заказ `canceled`; бит уже `sold` → `cancel` |
| **Оплата после `expired`** | заказ истёк (FR-29), деньги пришли: проверка прошла → `expired` → `paid`; не прошла → `canceled` |
| **Сумма `transfers` и комиссии** | расчёт для заказа из трёх Продюсеров с копейками; мок отвечает `400` на неверное распределение |

Ещё:
- таймаут ЮKassa → 3 повтора с одним ключом → `503`, резерв сохранён;
- падение между коммитом и `capture` → планировщик доводит платёж;
- окончательный отказ `capture` → бит снова `active`;
- сумма платежа не совпала с заказом → `cancel`;
- вебхук по неизвестному платежу → `200`;
- `PRICE_CHANGED`, `BILLING_REQUIRED`, `OWN_BEAT`, `LICENSE_INACTIVE`, FR-19;
- `428` для Exclusive без подписи;
- оба запроса FR-29;
- ссылки на скачивание: только владельцу и только для оплаченного заказа, срок ≤ 3600 с;
- договор: PDF создан, `pdf_sha256` совпадает с файлом;
- статистика продаж за период;
- отдельные тесты мока: идемпотентность, проверка сплитования, поломки.

## 11. Как вы сможете проверить и посмотреть своими глазами

1. Войдите Артистом (`SEED_ARTIST_*`), заполните «Данные покупателя».
2. Положите в корзину биты двух разных Продюсеров. Сейчас все демо-биты принадлежат одному Продюсеру, поэтому для наглядного сплитования демо-набор добавит второго Продюсера с несколькими битами (его логин и пароль будут в `.env.example`).
3. Оформите заказ → страница мока → «Успешная оплата» → страница возврата сама покажет ссылки на MP3 и договор.
4. Скачайте договор, сверьте `pdf_sha256` в «Моих покупках».
5. Пульт мока <http://localhost:8100/admin>: платёж, распределение денег по Продюсерам, кнопка «Отправить вебхук ещё раз» → в логе Core API видно, что дубль отсеян.
6. «Отказ банка» → заказ остаётся, «Оплатить снова» создаёт новый платёж.
7. Поломка «таймаут» на create в пульте → «Платёжный сервис временно недоступен».
8. Войдите Продюсером → «Мои продажи».
9. БД:
   - `SELECT * FROM payment_events;`
   - `SELECT action, entity, details FROM audit_log ORDER BY id DESC LIMIT 10;`
   - `SELECT status, reserved_until FROM beats WHERE id = …;`
10. Резерв без ожидания 15 минут: в `.env` можно сократить `RESERVATION_TTL_MINUTES` и `DOWNLOAD_LINK_TTL_SECONDS` для демонстрации.

## 13. Оценка и порядок

Сложность **XL**, самый ответственный срез. Предлагаю три части, с коротким показом после каждой, как в срезе 1:

- **3a. Корзина и заказ:** корзина, заказ с резервом и снимком, договор-оферта (строка в БД), FR-29, экраны «В корзину», «Корзина», начало оформления. Проверка — гонка за Exclusive.
- **3b. Платёж и вебхук:** мок ЮKassa с пультом, платёж со сплитованием, вебхук, FR-23…FR-25, доведение зависших платежей, оплата из браузера и страница возврата.
- **3c. Выдача:** PDF договоров, ссылки на скачивание, «Мои покупки», «Мои продажи», письма, итоговый отчёт.
