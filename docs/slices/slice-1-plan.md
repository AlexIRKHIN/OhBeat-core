# Срез 1. Публикация бита и «Мои биты» — план

Статус: **ждёт «ок» аналитика**. Общий план — [PLAN.md](../PLAN.md). Диаграммы: `assets/sequence_beat_publication.png`, `assets/bpmn_beat_publication.png`, `assets/src/beat_lifecycle.puml`.

## 1. Что получится

Продюсер открывает «Загрузить бит», заполняет форму (UI-спецификация §1, AC-1…AC-5) и выбирает WAV, обложку и ZIP со стемами. Файлы параллельно летят прямо в MinIO, у каждого свой прогресс-бар. Через несколько секунд в «Моих битах» бит становится «Опубликован» или «Отклонён» с причиной, а в логе появляется письмо Продюсеру. Пока бит обрабатывается, в RabbitMQ UI видно, как проходит сообщение, а в MinIO — как файлы раскладываются по бакетам.

## 3. Новые термины

- **Presigned POST** — разрешение от Core API загрузить *один* файл прямо в S3. В нём ключ файла, срок (1 час) и предел размера (`content-length-range`), всё подписано секретом. Слишком большой файл S3 отвергнет сам. В срезе 0 так грузился аватар.
- **HeadObject** — запрос к S3 «есть ли такой файл и какого он размера», без скачивания самого файла.
- **Transactional outbox** — способ не потерять сообщение. Вместо того чтобы сразу слать его в RabbitMQ (а вдруг брокер недоступен), Core API кладёт его строкой в таблицу `outbox` в той же транзакции, что и смену статуса бита. Либо сохранится и статус, и сообщение, либо ничего.
- **Relay** — фоновый процесс, который раз в секунду забирает неотправленные строки из `outbox`, публикует их в RabbitMQ и отмечает `published_at`.
- **Publisher confirm** — подтверждение от RabbitMQ: «сообщение принято и записано». Только после него relay отмечает строку отправленной.
- **ACK / NACK** — ответ потребителя брокеру. ACK: «обработал, можно удалить». NACK: «не смог». Пока нет ни того ни другого, сообщение не пропадёт: если Worker упадёт, брокер отдаст его снова.
- **Очередь задержки** — очередь, где сообщение «лежит» заданное время (TTL), а потом само возвращается в рабочую очередь. Так делаются повторы через 30 с, 2 мин и 10 мин.
- **DLQ (Dead Letter Queue)** — «отстойник» для сообщений, которые не удалось обработать даже после всех повторов. Их разбирает Администратор (срез 5).
- **Идемпотентность** — повторная обработка того же сообщения не меняет результат. Нужна потому, что доставка устроена по принципу «как минимум один раз».
- **ffprobe / FFmpeg** — утилиты для анализа и конвертации аудио. ffprobe читает, что внутри файла на самом деле (формат, кодек, длительность), а не верит расширению.

## 4. Как пройдёт бит через систему

Это шаги диаграммы `sequence_beat_publication.png`:

```
Браузер ──POST /beats──► Core API ──► БД: beats(uploading), beat_prices, beat_genres, beat_files(временные ключи)
   │◄── 201 + presigned POST на каждый файл
   ├──► MinIO temp-uploads: master.wav, stems.zip, cover.jpg   (параллельно, мимо Core API)
   └──POST /confirm──► Core API ──HeadObject──► MinIO
                         └─► одна транзакция: beats.status = processing + INSERT outbox
                                   │
   Relay (раз в 1 с) ──► RabbitMQ media.events ──beat.media.process──► beat_processing_queue
                                                                            │
   Media Worker ◄─────────────────────────────────────────────────────────────┘
     скачать из temp → ffprobe WAV → ZIP: целостность, только WAV, антивирус → обложка
     ├─ не прошло → beat.media.processed {result: rejected, error} ─┐
     └─ прошло → MP3 320 + превью 128 с войстегом → private-media / public-media
                 → beat.media.processed {result: processed, outputs} ─┤
     ACK команды                                                       ▼
   Core API (потребитель результатов) ◄── beat_results_queue
     UPDATE beats ... WHERE status = 'processing' → beat_files (постоянные ключи) → письмо Продюсеру → ACK
```

**Что где оказывается:**

| Шаг | БД | RabbitMQ | MinIO |
| --- | --- | --- | --- |
| `POST /beats` | `beats` (`uploading`), `beat_prices`, `beat_genres`, `beat_files` с временными ключами (GAP-53) | — | — |
| Загрузка | — | — | `temp-uploads/raw/{id}/…` |
| `confirm` | `beats.status = processing`, строка в `outbox` | — | — |
| Relay | `outbox.published_at` | сообщение в `beat_processing_queue` | — |
| Worker | — | результат в `beat_results_queue` | `private-media/beats/{id}/master.wav`, `stems.zip`, `clean.mp3`; `public-media/previews/{id}_v1.mp3`, `covers/{id}_v1.jpg` |
| Результат | `beats.status = active / rejected`, `beat_files` с постоянными ключами | — | — |

## 5. Топология RabbitMQ

| Exchange | Очередь | Ключ | Особенности |
| --- | --- | --- | --- |
| `media.events` (direct) | `beat_processing_queue` | `beat.media.process` | DLX → `media.dlx` |
| `media.events` | `beat_results_queue` | `beat.media.processed` | DLX → `media.dlx` |
| `media.retry` (direct) | `beat_processing_delay_30s`, `_2m`, `_10m` | `beat.media.process.30s` … | TTL; по истечении — обратно в `media.events` (`beat.media.process`) |
| `media.retry` | `beat_results_delay_30s`, `_2m`, `_10m` | `beat.media.processed.30s` … | так же для результатов (GAP-20) |
| `media.dlx` (direct) | `beat_processing_dlq`, `beat_results_dlq` | имя очереди | DLQ |

**Как устроены повторы.** При временной ошибке (S3 недоступен, антивирус «упал») Worker считает, сколько раз сообщение уже прошло через очереди задержки (заголовок `x-death`). Попыток меньше трёх — копия кладётся в нужную очередь задержки (30 с → 2 мин → 10 мин), оригинал получает ACK. После третьего повтора — NACK, и брокер сам переносит сообщение в DLQ. Файл, не прошедший проверку (вирус, длительность), — это не сбой: Worker сразу публикует `rejected` и делает ACK. Почему не чистый NACK на каждом шаге — см. GAP-51.

**Проверки Worker'а и коды отклонения:**

| Проверка | Код в `error.code` |
| --- | --- |
| WAV — это PCM по данным ffprobe, а не по расширению | `INVALID_WAV` |
| Длительность WAV ≤ 10 минут | `WAV_TOO_LONG` |
| ZIP читается, контрольные суммы сходятся | `ARCHIVE_CORRUPTED` |

| Антивирус (мок) | `VIRUS_FOUND` |
| Обложка: JPG/PNG/WebP по сигнатуре, 1:1, ≤ 2048 px | `INVALID_COVER` |
| Исходники уже удалены lifecycle-правилом (GAP-22) | `SOURCE_FILES_EXPIRED` |

## 9. Экраны

- **«Загрузить бит»** по UI-спецификации §1, поле за полем:
  - обложка с мгновенной миниатюрой и проверкой 1:1 и 2048 px до загрузки;
  - BPM, в котором нельзя набрать буквы, минус и дробь;
  - тональность из списка без значения по умолчанию;
  - жанры: блокируются после третьего;
  - описание со счётчиком символов;
  - зоны WAV и ZIP: перетаскивание или проводник; при неверном файле — красное уведомление без старта загрузки; подсказка «Нужен для Trackout и Exclusive»;
  - сетка из четырёх лицензий с чекбоксами;
  - кнопка неактивна, пока есть ошибки.

  После `201` — параллельная загрузка с прогресс-барами. При обрыве — toast и «Повторить» для незагруженных файлов; если формы истекли, они сами перевыпускаются. `422` подсвечивает конкретный файл. После `202` — зелёное «Бит загружен и обрабатывается» и переход в «Мои биты».
- **«Мои биты»:**
  - список со статусами и причиной отклонения;
  - пока есть биты в обработке, список сам обновляется каждые 5 с;
  - изменение цены и включение лицензии прямо в списке;
  - «Снять с продажи» / «Вернуть»;
  - «Удалить» с модальным подтверждением (NFR-20);
  - для отклонённого — «Загрузить заново»: форма откроется с заполненными метаданными.
- В шапке у Продюсера — пункты «Мои биты» и «Загрузить бит».

## 10. Тесты

**Обязательный:** повторная доставка сообщения из очереди. Тот же `beat.media.processed` приходит 2–3 раза, в том числе одновременно → бит меняется один раз, письмо одно, на каждую доставку ACK. Тот же `beat.media.process` обрабатывается дважды → те же ключи в S3, в итоге один результат.

**Core API:**
- FR-6: границы полей (название 2/3/60/61 символ, BPM 39/40/300/301, жанры 0/1/3/4, цены 99/100/500000/500001), неизвестные жанр и тональность, стемы обязательны для Trackout и Exclusive, неверные расширение, MIME и размер, стоп-слово в названии и в описании, пользователь без роли Продюсера → `403`.
- FR-7: файла нет → `422` со списком; повторный `confirm` → `409`; после успеха в одной транзакции и статус `processing`, и строка в `outbox`.
- MinIO отвергает файл больше лимита из политики.
- Relay: публикует и отмечает строки; если упал между публикацией и отметкой — отправит повторно, и обработка это переживёт.
- Результаты: `processed` → `active`, `published_at`, 5 строк `beat_files`, письмо; `rejected` → причина; результат для бита не в `processing` → ACK без изменений.
- Цены и статусы: правила `LAST_ACTIVE_LICENSE`, `STEMS_REQUIRED`, `BEAT_SOLD`, переходы `PATCH` и `DELETE`, чужой бит → `403`.
- FR-8: бит в `uploading` старше 24 ч → `deleted`, свежий не трогается.

**Media Worker** (на настоящем FFmpeg и образцах файлов): каждый код отклонения из таблицы выше; успешная обработка (длительность, битрейты 320 и 128, `Cache-Control` у превью); временная ошибка → 30 с → 2 мин → 10 мин → DLQ (на настоящем RabbitMQ, с сокращёнными задержками).

**Сквозной:** `confirm` → relay → Worker → результат → `active` на всём живом окружении.

**Фронтенд:** правила формы (BPM, жанры, цены, стемы, проверка файлов).

## 11. Как вы сможете проверить и посмотреть своими глазами

1. Сгенерировать образцы: `docker compose run --rm media-worker python -m worker.samples` → папка `samples/` (хороший WAV, WAV на 11 минут, MP3 с расширением `.wav`, ZIP с `.exe`, ZIP с EICAR, обложка 3:2).
2. Войти Продюсером, загрузить хороший бит → «Обработка» → через несколько секунд «Опубликован».
3. RabbitMQ UI (<http://localhost:15672>), вкладка Queues: счётчики сообщений в `beat_processing_queue` и `beat_results_queue`.
4. MinIO Console: файлы бита в `temp-uploads`, `private-media`, `public-media`. Скачать превью из `public-media` и послушать войстег.
5. Логи: `docker compose logs -f media-worker media-results` — каждый шаг обработки и текст письма Продюсеру.
6. БД: `SELECT id, status, rejection_reason FROM beats;`, `SELECT * FROM outbox;`, `SELECT kind, storage_key, size_bytes FROM beat_files WHERE beat_id = …;`.
7. Отклонения: загрузить каждый плохой образец и увидеть причину в «Моих битах».
8. Повторы и DLQ своими глазами: включить в `.env` `ANTIVIRUS_MODE=unavailable`, перезапустить Worker, загрузить бит с ZIP. В RabbitMQ UI видно, как сообщение переходит в очереди задержки, а потом в `beat_processing_dlq`. Бит при этом остаётся «Обработка» — его разберёт Администратор в срезе 5.
9. Обрыв связи: во время загрузки включить в DevTools режим Offline → toast и «Повторить».

## 12. Новые GAP

GAP-50…GAP-56 — в [GAPS.md](../GAPS.md). Самые заметные:
- **GAP-51:** одним NACK нельзя выбрать задержку 30 с / 2 мин / 10 мин, поэтому повтор делается копией в очередь задержки, а NACK используется только для DLQ;
- **GAP-50:** в сообщении-результате нет размеров и хэшей файлов, а `beat_files.size_bytes` обязателен;
- **GAP-53:** где хранить, какие файлы заявлены, пока бит в `uploading`.

## 13. Оценка и порядок

Сложность **XL**, самый объёмный срез. Предлагаю три части, с коммитами и коротким показом после каждой:

- **1a. Core API:** `POST /beats`, загрузка, `confirm`, outbox и relay, «Мои биты» в API, цены и статусы, планировщик FR-8. Проверка — Swagger, RabbitMQ UI (сообщение дошло до очереди) и тесты.
- **1b. Media Worker и результаты:** проверки, FFmpeg, войстег, раскладка, повторы и DLQ, потребитель результатов, письма. Проверка — бит становится `active` или `rejected` через API.
- **1c. Экраны:** «Загрузить бит» и «Мои биты», ручная проверка в браузере, итоговая таблица и отчёт.
