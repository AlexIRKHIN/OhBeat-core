# Срез 5. Итоги

Дата: 12.11.2026. План — [slice-5-plan.md](slice-5-plan.md).

## Что сделано

- **Core API, модуль `backend/app/admin/`** (только роль `admin`):
  - Audit Log: фильтры по действию (точно или группой `payment.`), сущности, ID и периоду по Москве; курсор; значения для меню фильтров (`/audit-log/facets`). Изменять журнал API не умеет — `405`;
  - жанры: список с числом битов, добавление (без повторов без учёта регистра), удаление только неиспользуемых — иначе `409 GENRE_IN_USE`;
  - стоп-лист: слова и фразы, хранятся так же, как сравниваются (нижний регистр, «ё» → «е»);
  - зависшие биты: в `processing` дольше `STUCK_PROCESSING_MINUTES` (30) с последней задачи в `outbox` (GAP-74). «Повторить» ставит ту же задачу заново, «Отклонить» переводит бит в `rejected` с причиной и отправляет письмо Продюсеру. Все действия пишутся в Audit Log.
- **Общая функция `enqueue_processing`:** задачу для Media Worker теперь ставят из одного места — подтверждение загрузки и «Повторить» Администратора.
- **Экран `/admin`** с вкладками «Журнал», «Жанры», «Стоп-лист», «Зависшие биты». Вкладка хранится в адресе. Удаление — через окно подтверждения, отклонение — через окно с полем причины. Работает на ширине 375 px.

## Экскурсия по коду

- **Сервис:** [`admin/service.py`](../../backend/app/admin/service.py). В шапке — три части раздела. Самое интересное — `_processing_since`: время последней задачи бита в `outbox` достаётся подзапросом по JSON-полю `payload->>'beat_id'`. Так мы обошлись без новой колонки (GAP-74).
- **Постановка задачи Worker'у:** `catalog/service.py` → `enqueue_processing`. Раньше этот код жил внутри `confirm_upload`, теперь его вызывает и Администратор.
- **Экран:** [`pages/AdminPage.tsx`](../../frontend/src/pages/AdminPage.tsx) — по компоненту на вкладку; правила фильтра — `lib/admin.ts`.

## Как проверить руками

1. Войдите Администратором (`SEED_ADMIN_*` в `.env`) → «Администрирование».
2. **Журнал:** выберите в «Действие» группу `payment.*`, затем `contract.signed`. Нажмите «Подробности» — увидите `draft_sha256` и маску телефона.
3. **Жанры:** добавьте жанр, попробуйте добавить его же другими буквами, удалите. У Trap удаление недоступно.
4. **Стоп-лист:** добавьте слово, войдите Продюсером, попробуйте назвать бит этим словом → «Запрещенное слово».
5. **Зависший бит.** Задержки повторов (30 с, 2 мин, 10 мин) зашиты в параметры очередей RabbitMQ: если поменять их в `.env`, RabbitMQ откажется заново объявить существующие очереди. Поэтому проверка идёт с настоящими задержками:
   - запустите Worker со «сломанным» антивирусом, не трогая `.env`:
     ```bash
     ANTIVIRUS_MODE=unavailable docker compose up -d media-worker
     ```
   - загрузите бит **со стемами** (антивирус проверяет только ZIP);
   - через ≈13 минут сообщение окажется в `beat_processing_dlq` — видно в <http://localhost:15672> → Queues;
   - через 30 минут бит появится во вкладке «Зависшие биты». Сразу его видно по флажку «Показать все в обработке»;
   - верните исправный антивирус: `docker compose up -d media-worker` → «Повторить обработку» → бит опубликован, Продюсеру пришло письмо (`docker compose logs media-results | grep EMAIL`).
   - Порог можно уменьшить: `STUCK_PROCESSING_MINUTES=15` в `.env`, затем `docker compose up -d api`.

## Что важно знать

- **Отличие от плана.** В плане для ручной проверки были «короткие задержки повторов». На деле их не поменять без пересоздания очередей, поэтому проверка идёт с настоящими задержками (см. выше). Стоп-лист принимает не только слова, но и фразы: проверка со среза 1 так и работала (GAP-76 уточнён).
- **Старое сообщение остаётся в DLQ** после «Повторить» (GAP-77). Его можно посмотреть и удалить в веб-интерфейсе RabbitMQ; на работу системы оно не влияет.
- **Новые GAP:** 74–77.
- **Все пять срезов готовы.** Остался финал: сквозной автотест всего пути, запуск с нуля одной командой и README.
